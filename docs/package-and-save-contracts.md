# Package and save contracts

## `.realmz2`

A deterministic ZIP contains canonical minified JSON and content-addressed media:

- `manifest.json`: format/version, campaign/content IDs, compiler provenance, engine requirements, start location, capability inventory, file hashes, package hash.
- `content.json`: Realmz definitions and text.
- `world.json`: maps, authoritative topology, APs/XAPs, transitions, random rectangles, timed encounters, and immutable metadata.
- `scenario.json`: Classic instructions, Scenario Action programs, state definitions, and migrations.
- `assets/index.json` plus hashed media payloads.

Providence owns the schema. The runtime mirror under `contracts` is byte-identical and independently enforced. The package excludes editor layout, absolute paths, native raw bytes, compatibility annexes, and archaeology artifacts.

Realmz application content and scenario content are separate authorities. Rebuilt ships the complete stock Realmz library once: rules records, strings, fonts, controls, integrated media, and other application resources. A campaign package contains only scenario-owned records/media and normalized references to stock identities. A package may carry an exact type-and-ID replacement only where Castle proves that the scenario resource chain can override the application resource. Providence validates those references against the pinned Rebuilt application contract; it does not duplicate stock application payloads into each campaign. The current schema-v3 exporter still repeats several stock definition tables in campaign `content.json`; that is a blocking contract defect scheduled for the next package-contract cut rather than an accepted exception to this ownership rule. Runtime decoding must prefer Rebuilt's application authority wherever a stock field has already migrated, beginning with standard spell descriptions.

Schema v3 is the sole supported runtime contract. The mirrored schema is SHA-256 `12376856235a11f507b993835acad87b546f87b9ad519533967ed2701ddb89cd` from Providence commit `efee09f5ce05de7000dacf20efb0ebbc72bcd047`. Manifests use format version 2 and all five canonical documents use schema version 3. Versions 1 and 2 are rejected explicitly and must be re-exported; no runtime adapter or defaulting branch survives the cutover. V3 retains the normalized display, rules, encounter, topology, media, and application-hook data established by the unpublished v2 contract, makes runtime-required values compiler-owned inputs, and preserves Battle `distance` as an initial-placement field rather than a weapon requirement. Monster records preserve independent Classic name identity plus authored bestiary description/menu visibility. Maps preserve nullable base scale and the compact-cell forest semantic. Each occupied shop record preserves its unique native slot so category order and first-empty buyback placement remain deterministic save-owned behavior. Scenario-owned Custom 1–3 audio declares its independent slot. Opcode 92 alone carries ten operands compiled from two consecutive Extra Code rows; ordinary actions retain five. Timed records carry an exact `classicMacroId` and matching `xap:<id>` program reference because Castle dispatches Data ED3 directly; they do not masquerade as placed AP record indexes. Providence emits canonical `Land level N` and `Dungeon level N` playable-level names while preserving authored STR# player-map titles on player-map records only. Providence's canonical project and native compatibility annex remain outside the package. Canonical schema bytes use LF line endings so the compiler and runtime hash the same contract on Windows.

The schema-v3 world contract uses Providence's fixed row-major `realmz2.compact-cell-rows.v2` topology ABI. Castle's packed dungeon fields and Providence's Layout record remain compiler inputs, not runtime map models. Each compact cell tuple carries semantic flags, ordered directional edges/features, trigger and random-region references, base/overlay render identities, exact Classic `needboad`, and blocked-attempt timeclicks without repeating map IDs, coordinates, or JSON property names across 90×90 maps. Each land map also carries the active landlook's exact tile-60 removed-boat and tile-147 placed-boat profiles; dungeon maps require `null`. Runtime topology decodes cells lazily and applies session-owned boat-presence overlays through those immutable profiles, so movement, LOS, rendering, save restoration, and battlefield derivation see the same effective cell. Placed AP references compile in native record order and retain `classicRecordIndex`; duplicate record identities on one map fail validation. Placed AP headers compile to a typed `postActionLocation`; XAPs use `null`, and tile mutation remains an explicit scenario instruction. Random rectangles retain signed 1-in-10,000 chances, battle ranges, three random-door slots, only/option behavior, and media IDs. Its content contract carries direct Simple/Complex/Thief/Timed Encounter records, a distinct Classic option-label table, and direct race, caste, item, spell, monster, battle, treasure, and shop definitions. The base monster catalog represents Normal Monsters; optional typed sets `-1` and `1` contain complete reachable replacements from Data MD-1 and Data MD1 with unique stable identities. A package may not emit a partial set or ambiguous replacement. Providence merges 799 nonzero bundled Classic item identities with scenario supplies/overrides and compiles standard Data S records to packed class/level/slot identities; custom Data Spell slot 0 is packed ID 5101 and slot 104 is 5715. Monster weapon restrictions retain the signed Data MD byte as `requiredWeapon`; `magicToHit` is its independent weapon-plus threshold. Battle records retain their unrelated placement `distance`, explicit monster slots, coordinates, and traitor inversion. Its scenario contract contains trigger/program references, exact application-hook program IDs, preserved `ClassicAction` instructions, typed `CallScenarioAction` instructions, compiled Safe bytecode, versioned action-state definitions, and migrations. It does not contain Safe visual/source AST, behavior anchors, authoring modes, or sandbox source.

For every package with a reachable battle, `world.json` now carries immutable `battleTerrainSets` and each map identifies its effective set. A land set contains its active landlook records 0 through 200 followed by shared `Combat Data BD` records 201 through 400; the active landlook therefore wins Castle's overlapping tile 200 exactly once. The dungeon set contains shared records 200 through 400. Every tile retains signed sound, time, solid, boat, and forest values, exact boolean flags, and the 3×3 `combatBuild`; incomplete ranges or malformed builds fail both export and runtime construction. These are immutable construction inputs, not an alternate exploration topology. Tactical positions, battlefield generation, proximity-gated melee, and Guard/withdrawal reactions use session-owned combat geometry and serialized cursors. Ranged attacks remain disabled until projectile range, costs, and resolution are source-owned.

Managed Providence media and decoded imported scenario resource-catalog pictures/icons/sounds become content-addressed package payloads. Classic resource identity is the exact four-character type plus signed ID; case and trailing spaces are significant, and equal numbers in `PICT`, `cicn`, and `snd ` are unrelated resources. Scenario-managed media replaces the imported scenario-catalog entry for the same key. Realmz's integrated `snd ` bank is versioned application media and is not copied into every campaign; a packaged exact sound key is an explicit scenario override and resolves before the application fallback. Package ambiguity never falls through to a plausible built-in resource. Missing integrated media is a Realmz Rebuilt build/install defect, not a campaign-readiness defect. This deterministic composition preserves Castle's normal scenario-before-application result without exposing its mutable global resource-file cursor. Providence and the runtime independently reject duplicate package asset IDs and exact package resource keys. Application PICT/CICN migration remains resource-family-specific because current map, appearance, and battle contracts still carry package asset IDs. Every referenced map tileset is a required content-addressed PNG with explicit grid metadata; Providence normalizes Classic PICT 302's fixed dungeon-composition region to a 4×4 runtime atlas and, for reachable battles, emits the complete 20×20 image as the exact `classic-battle-tiles-302` battle atlas. Castle's effective combat graphics combine the active landlook for battle tile IDs 1–200 with that shared atlas for IDs 201–400. Classic positive and negative icon-backed land values compile as the landlook's base terrain plus an exact packaged `cicn` overlay when the scenario owns that resource, or a normalized application-CICN reference otherwise; neither form may masquerade as a tileset index. Absolute paths and resource-fork bytes never enter the package.

Every package also carries the complete selectable Classic character appearance catalogs: portrait `cicn` 257–376 and tactical `cicn` 9000–9119. Each effective entry has an explicit `portrait` or `combat-icon` role, stable asset identity, decoded PNG dimensions, and ordinary exact-key precedence. Providence and the runtime both reject a missing, duplicate, wrongly typed, or undecodable entry. Castle's Human Data Race value stores portrait set zero even though the browseable Portraits fork starts at 257; `FD-CHARACTER-002` deliberately aliases set zero to the first real six-image set rather than requesting unavailable `cicn` 251–256.

`PackageRepository` rejects unsafe/extra entries, noncanonical entry order, schema or capability drift, per-file size/hash mismatches, package-hash mismatches, malformed topology, duplicate identities, incomplete character appearance catalogs, unresolved map/trigger/program/action references, unsupported Classic opcodes, invalid Scenario Action namespaces or callers, argument/type mismatches, oversized Safe programs/arrays, and unknown capabilities before constructing `RealmzContent`. `realmz.scenario.gdscript-actions-v1` is a recognized but unavailable capability and fails readiness until an OS-confined external host exists.

Installed-package discovery is deliberately staged. It verifies manifest/schema/capability metadata and deterministic inventory without parsing topology or constructing campaigns merely to draw the library. Generic discovery retains every immutable content-hash revision for diagnostics; the campaign selector groups valid revisions by campaign ID and exposes the most recently installed file only. The application also discovers the exact provenance-pinned 13-scenario Castle bundle from immutable release resources, then overlays valid user-installed revisions by campaign ID. Selecting a bundled baseline runs the ordinary complete validation and installs the exact bytes under `user://packages`; bundled scenario location is not a trusted-package shortcut. Importing any external `.realmz2` follows that same integrity and typed-validation path, copies the exact bytes transactionally, and writes a durable app-owned receipt containing its compressed archive hash and immutable file identity. Subsequent Play operations verify the receipt's byte count and modification identity plus schema/campaign/package manifest identity before constructing Providence's compact typed content; they do not rehash the archive, rehash every ZIP payload, or repeat compiler-level media/reference validation. If the installed archive changes, the receipt is invalid and the package must be reinstalled. An in-process typed cache remains an additional optimization, never the only trust record.

## `.r2save`

Save v4 is a clean typed boundary. A versioned envelope under `user://saves/<campaign-id>/` records campaign/package identity, rules and fidelity decisions, and one detached `SessionSnapshot`. The snapshot contains complete `GameState`, overlays, clock, mutable economy—including base-shop quantity overrides and paired buyback quantity/native-slot maps—combat and reward state, scenario replacements, VM frames, Scenario Action state, RNG state and draw count, pending interaction, and the exact session continuation needed to resume the committed boundary. Presentation state and the bounded debug RNG trace are never saved.

Every closed protocol variant—including intent payloads where persisted, interaction requests and responses, VM/session continuations, and nested workflow state—encodes as `{kind, version, data}`. Its codec requires the exact fields for that kind and rejects unknown kinds, versions, or fields before constructing a session. JSON dictionaries remain inside the infrastructure codec; `GameSession`, core workflows, and scenario code receive typed values only.

Versions 1 through 3 are intentionally incompatible. They are reported to the user as belonging to an older Realmz Rebuilt save contract and are never migrated or partially interpreted. There is no Classic or prior-Remake save importer.

Saving is allowed only at committed session boundaries, including party setup with a partial party. Infrastructure writes a temporary file, decodes and validates it through the same strict v4 codec, rotates one backup, and atomically replaces the slot. Restore validates a complete replacement—content identities, carried-load totals, shop slot bands and collisions, requests, continuations, VM state, combat ownership, and RNG position—before changing the active session. Failure leaves the current session untouched.

## `.r2char`

Reusable character revisions are separate from `.r2save`. A record contains a stable character ID, immutable revision hash, rules version, source campaign/package provenance, publication metadata, complete detached character state, inventory/spells, and source revision. `CharacterVaultRepository` stores revisions under `user://characters/<character-id>/`, validates the requested character and revision identities on every read, retains one recoverable backup, and archives instead of deleting. The host exposes current and earlier immutable revisions, exact target-campaign eligibility, archive confirmation, and recovery without allowing presentation to touch files. Import is a typed session intent; eligibility failures identify missing definitions, restrictions, level limits, incompatible race/class relationships, unavailable/wrong-role portrait and combat-icon IDs, or an exact item-instance ID already owned by the assembled party. The session never rewrites a conflicting instance identity: it rejects the import before mutation, and aggregate restore enforces the same one-owner invariant across inventories, party storage, equipment escrow, and combat fumble custody. The session recomputes personal carried load from the target package's immutable item weights and the imported wealth rather than trusting a stale revision total; an over-limit result is ineligible without stripping or substituting content. Finalizing a newly created character yields a typed, saveable publication confirmation. Acceptance publishes only after the session has committed the character and cleared the interaction; decline has no repository side effect. Ordinary campaign changes never write back implicitly.

Character revision storage remains independent from save v4. `SaveRepository` owns only the strict v4 envelope transaction; `CharacterVaultRepository` continues to own validated immutable `.r2char` revisions and their separate compatibility rules.
