# Inventory

`ItemDefinition` describes authored content; `ItemInstance` records the portable mutable item. `RealmzContent.items` exposes the active `ItemCatalog`, built after application definitions and scenario exact-ID overlays are composed. `InventoryRules` owns item-use admission, capacity, transfer, load, Split, Join, charge, removal, and restoration. `EquipmentRules` owns wearable admission, equip/unequip mutation, scroll-case presence, and the combat loadout projection. `RealmzRules` exposes both collaborators directly, so a caller asking about equipment does not route through an inventory facade. The matching transactions live under `src/playthrough/inventory`: `InventoryWorkflow` coordinates equip, unequip, trade, Split, and Join through `GameSession`; `FieldItemWorkflow` owns Identify, Torch, door items, and charged spell items rather than hiding those operations in a combined inventory-and-magic owner.

The Inventory scene may display only detached `ItemView` facts and provided action availability. Hidden identity and curse information must not be inferred in presentation. Begin behavioral work in `tests/integration/test_inventory_session.gd`; begin layout work at `src/ui/inventory/inventory_screen.tscn`.

`inventory_screen.tscn` embeds the reusable `inventory_workspace.tscn` used by both the ordinary route and Encounter item selection. That workspace owns the normal browser/command/inspector split plus the alternate state host. The character summary, item actions and confirmation, selected-item record, empty state, and complete two-ledger Trade composition are neighboring editable scenes. Variable party members, item rows, facts, trade portraits, and trade items instantiate the exported component scenes; `InventoryScreenController` binds their detached identities and emits intents without constructing Controls. `InventorySceneBinding` owns the repeated label, media, connection, child-cleanup, and scroll-restoration mechanics so the route controller remains focused on Inventory state and commands.

Encounter Items retains the same mounted task while the application changes between Wide and Compact. `InteractionPresenter` forwards the live profile to `EncounterInteraction`, which reapplies it to `InventoryScreenController` and rebinds the existing workspace; this changes scene-owned minimums without replacing the interaction or losing its request-owned item catalog. A sole eligible character receives a visible bound name, while an ordinary party selector remains a compact portrait row.

Player commands enter through `InventoryIntents`: use and targeted use carry `InventoryIntentPayloads.Use` or `Target`, while equip, unequip, drop, split, join, and trade share the explicit `Action` value. The factory fixes the command kind so callers cannot accidentally pair an inventory payload with an unrelated operation.

Saveable item targeting, drop confirmation, and item-owned XAP handoffs are created by `InventoryContinuations` beside the workflows. Their typed `TargetingContinuationBody` or `ItemXapContinuationBody` enters the central continuation codec only when a save is written or restored.
