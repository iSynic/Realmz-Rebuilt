# Scenario VM evidence

This document separates the Classic control-flow observations used to design the 2.0 VM from the behavior proven in the new runtime. It does not claim a Castle runtime fixture where only source has been inspected.

## Castle source/control-flow

Pinned oracle: Realmz Castle commit `491816ad60037394f92c428e99c004494d3c28b3`.

- `src/realmz_orig/newland.c:2010-2058` moves opcode 20 to its destination and jumps to `recheck` for a marked Action Point, replacing the executing action record; `recheck` at lines 70-93 returns on an absent, disabled, or failed-chance destination. Rebuilt hands that destination check to the session after finishing the entire issuing VM timeline, including an enclosing repeating encounter. A single-frame return instead reopens the old encounter before the session receives the handoff. Synthetic restored direct and signed-GOSUB encounter cases protect this distinction, while the existing unmarked-destination test retains ordinary continuation. Start Game completion also forwards this event into the ordinary depth-one post-move check, so it cannot silently discard the destination AP. The locally installed Dead of Night opening reproduced the loop through both choices: Simple Encounter 1 branches through XAP 21 or 22 to land 0 at (14, 6) or (16, 64), whose destination APs end with Keep Codes. Controlled Begin Adventure execution now runs AP 96 or 97 once and finishes without a pending encounter; both routes also pass save-envelope round-trip and restore at every opening choice and acknowledgement. This is source-control-flow and controlled Rebuilt execution evidence, not a new Castle runtime capture or campaign-completion claim.

- `src/realmz_orig/misc.c:316-324` reads `Data EDCD` by seeking to the requested zero-based ID times ten bytes and reading five signed 16-bit words. It does not check the read result before using the global buffer. Complete records therefore have a source-established Extra Code interpretation, but a trailing fragment alone does not establish an intended authored row: truncation, padding, or editor residue remain possible. Providence retains the exact fragment in source truth and exports schema-v5 candidate-row/count metadata. Rebuilt prepares a typed failure for consuming instructions, including opcode 92's second row, before any effects or RNG use. It never pads operands or reproduces stale-buffer reads. The host logs the resulting fault with campaign, program, slot, opcode, row, and byte-count context. Controlled preservation tests prove unrelated instructions continue, a selected incomplete row fails before a tile mutation or following instruction, and non-EDCD operands do not acquire this guard. These are source and synthetic-runtime proofs, not a Castle partial-read execution capture.
- `src/realmz_orig/encounters.c:294-340` treats Simple Encounter result zero as an eliminated choice, substitutes the eliminated label, and loops after its feedback sound if clicked. Imported Rebuilt packages retain that native identity and source label; the existing eliminated-choice presentation excludes it, and stale selections are rejected before consuming an attempt. Zero does not require an executable result or constitute a broken reference. Other unavailable imported result IDs remain deferred references.

- `src/realmz_orig/newland.c:95-108,3721-3723` iterates eight instruction slots and dispatches through a switch without an outer default. Imported Rebuilt definitions preserve these values and publish a `classic-unrecognized-skipped` trace. `test_imported_instruction_preservation.gd` proves preservation, continuation to the next instruction, and strict fresh-definition rejection; Providence's `unknown_opcode_inventory_includes_unreachable_source_occurrences` proves the durable import inventory includes unreachable unknown values. - `src/realmz_orig/newland.c:1966-1990` branches opcode 17 on monster-macro mode: its direct or queued dead-monster position becomes the center passed to `spelltargets`, rather than using picked characters. `spelltargets.c:9-119` first queues a nonzero `queicon` field at that exact center, then applies the Data AD mask or fixed side-group selector and handles reflection before ordinary resolution; `resist.c:34-37` retains the active actor as the resistance caster. The typed `reopenResult` choice continuation retains that distinction through save/restore; opcode 41 remains elimination without immediate reopening.

The 2.0 VM therefore carries origin context across opcode 39 and directive-based XAP transfers instead of replacing the frame with contextless code.

In `src/realmz_orig/textbox-time.c:6-105`, class `-1` enables a click wait for a positive message index and disables it for a negative index; the click path waits for mouse or keyboard input and erases the textbox before returning. The 2.0 VM therefore yields a serializable `acknowledge` interaction for positive opcode 1 messages and continues immediately after publishing negative messages.
- `src/realmz_orig/newland.c:1530-1535` passes Classic opcode 3's two Extra Code option IDs to `question2`. `src/realmz_orig/question.c:100-134` keeps the standard Yes/No dialog when the first ID is zero; otherwise it reads 25-byte labels from Data OD, falling back to ordinary Data SD2 messages only when Data OD is unavailable. Mode four sets the instruction cursor beyond the eight-slot timeline; it does not mutate an encounter option despite the source comment, and the ordinary epilogue still runs. `src/realmz_orig/moveparty.c:31-35,65-69` confirms that the negative movement is land-only and preserves the party-facing delta. Realmz 2.0 therefore reports these two control-flow outcomes explicitly: the session reverses a post-move land AP before finalization, destination handling, or random checks, while the VM finishes mode four without executing a later slot.
- `src/realmz_orig/newland.c:1826-1828` forwards opcode 9's signed operand to `sound`. `src/realmz_orig/misc.c:1875-1907` rotates through the configured sound channels, looks up the absolute `snd ` ID, plays a positive ID asynchronously, and a negative ID synchronously. The 2.0 world/time handler reproduces that result against the authoritative map dimensions instead of rejecting Tutorial's valid random edge rolls; dungeon overshoots remain an explicit safe-runtime failure because Castle's corresponding field access is unchecked.
- `src/realmz_orig/newland.c:351-404` guards opcode 122 with active combat, no live spell execution, enabled fumbles, a committed physical action, and `q[up] < 10`. `getbattleorder.c:24-80` encodes monsters as 10 and above, making the nested monster branch unreachable. Authored Extra Code sound/text occurs only after that outer guard. The 2.0 handler therefore suppresses both media and mutation for a nonphysical or monster-active invocation, then delegates a valid party weapon mutation to `CombatFlow`; it does not inherit Remake's reachable monster path. The exact live-`inspell` fact remains disabled until spell activation owns an equivalent lifecycle boundary.

These observations establish structure and control flow. They do not by themselves prove every edge case of the Castle executable.

## Borrowed interpreter concepts

Current Remake checkpoint `cdaa0d8dcc5ab81c195aa960c860bf74e7d4f40b` demonstrates useful serializable interpreter concepts in `src/scripts/scenario_runtime/scenario_interpreter.gd:840-875`: trigger/cursor identity, call stack, encounter origin, pending command, trace, and restore validation. ## State & Progression Control-Flow Branch Family (Opcodes 46, 72, 77, and 86)

A focused compatibility batch closed the distinct variant signatures for the state and progression control-flow family under `FD-SCENARIO-011`. These opcodes share Castle's destination branching model (`forcebranch` in `newland.c:2739` and `switch(extracode[2])` in `newland.c:202,1318,2938`), signed GOSUB stack tracking, and target routing.

### Distinct Variant Signatures and Source Semantics

1. **Opcode 46 (Branch on Quest)**:
   - Condition selectors: `0` (branch if quest unset), `1` (branch if quest set), `2` (force branch unconditional).
   - Out-of-bounds safe completion: *Wrath of the Mind Lords* `xap:489` stores malformed Extra Code `[274, 274, 304, 30003, 420]`. Because condition 274 is neither 0, 1, nor 2, the branch is not taken and execution safely returns `completed(false)` without memory corruption or runtime crash.
   - Destination modes: mode `0` (XAP branch via `ScenarioVmDirective.branch_xap`), mode `-1` (dropout to slot 7 via `ScenarioVmDirective.dropout`), mode `1` (Simple encounter result via `ScenarioVmDirective.branch_program`), mode `2` (Complex encounter result), mode `3` (Keep Codes terminating the timeline via `ScenarioVmDirective.finish_timeline` with `action_point_kept`).
   - Signed GOSUB: negative opcode `-46` sets `action.gosub == true`, propagating `gosub: true` to the branch directive (e.g. *Wrath* `xap:377` `[4, 1, 0, 206, 0]`).
   - Typed validation: rows with fewer than 5 Extra Code words fail with `missing_extra_code`; unsupported destination modes fail with `unsupported_branch_mode`.

2. **Opcode 72 (Branch on Quest Range)**:
   - Evaluates whether all quests in the inclusive range `[first, last]` are set.
   - Fallthrough: if any quest in the range is unset, returns `completed(false)` with `allSet: false`.
   - Inverted range vacuous truth: when `first > last`, the loop does not execute and `all_set` remains `true`, matching Castle `newland.c:2933` (`smallreply = TRUE; for (tt = extracode[0]; tt <= extracode[1]; tt++) ...`).
   - Destination modes: mode `0` (XAP, e.g. *Wrath* `xap:898` `[16, 17, 0, 0, 899]`), mode `1` (Simple encounter), mode `2` (Complex encounter), with signed GOSUB supported.
   - Typed validation: quest indices outside `0..99` fail with `invalid_quest_range`; rows with fewer than 5 words fail with `missing_extra_code`.

3. **Opcode 77 (Branch on Quest Value)**:
   - Evaluates `quest_value(quest_id) >= minimum`.
   - Dual target routing: if matched, branches to true target `extra_code[4]`; if unmatched, branches to false target `extra_code[3]`.
   - Fallthrough routing: if the selected target is `0`, returns `completed(matched)` without branching.
   - Destination modes: mode `0` (XAP), mode `1` (Simple), mode `2` (Complex), with signed GOSUB (e.g. *Wrath* `xap:380` `[8, 3, 0, 0, 383]` with `gosub = true`, and `xap:437` `[9, 3, 0, 0, 440]`).
   - Typed validation: quest indices outside `0..99` fail with `invalid_quest`; rows with fewer than 5 words fail with `missing_extra_code`.

4. **Opcode 86 (Branch on Misc)**:
   - Test kinds:
     - `0`: caste present in party (`expected >= 0`) or among selected PCs (`expected < 0`).
     - `1`: race present in party (`expected >= 0`) or among selected PCs (`expected < 0`).
     - `2`: gender present in party (`expected >= 0`) or among selected PCs (`expected < 0`).
     - `3`: party in boat (`_game_state.party_in_boat`, e.g. *Wrath* `xap:1997` `[3, 0, 0, 1998, 0]`).
     - `4`: party camping (`_game_state.party_camping`).
     - `5`: caste class present in party (`expected >= 0`) or among selected PCs (`expected < 0`).
     - `6`: race descriptor bit `1..32` tested via `1 << (expected - 1)` in party or among selected PCs.
     - `7`: total party level sum > `expected`.
     - `8`: selected PC level sum > `expected`.
   - Selected-only negative expectations: `expected < 0` restricts evaluation to `_game_state.scenario_progress.selected_characters()` for kinds 0, 1, 2, 5, 6.
   - Target routing: true target `extra_code[3]`, false target `extra_code[4]`; target `0` falls through.
   - Destination modes: mode `0` (XAP), mode `1` (Simple), mode `2` (Complex), with signed GOSUB (e.g. *Wrath* `xap:792` `[0, 2, 0, 796, 0]`, *War* `xap:2815` `[1, 12, 0, 2816, 0]`).
   - Typed validation: test kinds outside `0..8` fail with `invalid_misc_branch`; race descriptors outside `1..32` fail with `invalid_race_descriptor`; rows with fewer than 5 words fail with `missing_extra_code`.

### Evidence Scope and Distinction

The 13 bundled packages contain stored occurrences of these opcodes (e.g. 2,901 stored opcode 46 rows, 15 stored opcode 72 rows, 88 stored opcode 77 rows, 168 stored opcode 86 rows). The public tests in `test_scenario_vm.gd` (`_test_state_and_progression_branch_opcodes`) prove controlled runtime execution of all distinct condition selectors, destination modes, signed GOSUB tracking, out-of-bounds error handling, and bundled representatives. These tests establish controlled execution through public runtime boundaries; ordinary-route reachability and full campaign certification across the thirteen bundled campaigns remain separate unproven progression work.
