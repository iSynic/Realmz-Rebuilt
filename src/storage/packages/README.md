# Package loading

Begin with `PackageRepository` when following installation or discovery, and with `PackageDomainAssembler` when following the conversion of verified JSON documents into immutable game content. The assembler coordinates public decoders and validators; it does not parse record families itself.

`ApplicationLibraryIdentity` names the one committed Providence-built stock library used by the application and ordinary developer probes. Its package and compact acceptance lock live in `application/`; change the path, campaign ID, package hash, and lock together when accepting a newly compiled application library.

The thirteen release campaigns and their provenance records live in `bundled_campaigns/`. They are immutable package inputs discovered through the same validation and installation path as an external campaign; this directory does not grant them a runtime trust bypass.

Folder import runs the bundled Providence service through `ClassicScenarioImportTask`, using a disposable capture and the application's stock library. Its versioned JSON events report preflight, progress, diagnostics, startup-file ambiguity, completion, and failure. Conversion does not authorize installation: the ordinary package validator and atomic installer must succeed before the imported library updates. Reports retain unknown native instructions even when conversion later fails.

Schema v5 adds explicit metadata for an incomplete `Data EDCD` tail while retaining v3/v4 readers. Complete ten-byte rows compile normally and all tail bytes stay in Providence's source archive. Package decoding prepares a typed fault for any instruction that reads that candidate row, including opcode 92's companion row. Selecting it fails before instruction effects and records the campaign, program, slot, row, and byte counts through the existing session-fault and host error-log path. An unused tail does not block import or unrelated gameplay.

`ImportedScenarioLibrary` stores campaign origin, available immutable revisions, explicit preferred revision, import date, authored version label when available, and diagnostic summaries separately from archives. It migrates installed packages on discovery and keeps imported copies of main campaigns visible. Changing the preferred revision affects new games only; save binding remains the exact campaign/package hash.

`CanonicalJson` is the one stable dictionary encoder used for package hashes and exact repository readback comparisons. Character Files and settings reuse this storage utility rather than maintaining subtly different canonical encodings.

`PackageContentDecoder` is the stable content-record entry point. Campaign metadata, messages, and option labels belong to `PackageStoryContentDecoder`; items, Races, Castes, and spells belong to `PackageCharacterContentDecoder`; monsters, battles, treasures, shops, and encounters belong to `PackageEncounterContentDecoder`. Collection operations preserve authored order and duplicate tracking while focused record helpers validate and build one definition at a time. `PackageWorldDecoder` applies the same boundary to topology maps and Classic player maps, including exact media-backed marker validation. Scenario bytecode has its own neighboring decoder.

The flat Providence Caste record becomes a `CasteDefinition` with named attribute and progression sub-definitions at this boundary. The attribute record owns save, attribute, condition, and strength arrays; the progression record owns stamina, combat, magic, ability, and victory arrays. The decoder assigns the remaining scalar policy fields explicitly after validation, and no transport dictionary crosses into the game model.

`PackageScenarioDecoder` constructs Classic programs and Safe Scenario Actions. Safe bytecode remains a bounded recursive data format: the decoder routes calls, control flow, terminal instructions, scalar values, containers, operators, and collection expressions through named constructors while preserving one shared complexity counter and the declared-capability gate.

All decoders share one diagnostic dictionary and fail closed. Do not return transport dictionaries beyond this folder, invent defaults for malformed authored data, or copy stock application records into a scenario. Application content is composed first and the scenario contributes only owned records or exact-key overrides.

Media validation deliberately has two phases. `PackageMediaValidatorResolver.validate_package_assets` proves the scenario archive's own index, payload paths, hashes, dimensions, local keys, and music slots. `PackageMediaComposer` then overlays those typed records over application media only by exact Classic `(resourceType, resourceId)` key. Only that effective catalog is used to validate required appearances, battle capabilities, topology render references, monster art, player maps, and scenario references. The load result still exposes a scenario-only `PackageMediaCatalog`, preserving which ZIP owns each byte while presentation performs the same scenario-before-application lookup.

After composition and validation, `PackageDomainAssembler` builds `RealmzContent` as a directory of feature-owned immutable catalogs. Story and encounter triggers live under `content.scenario_records`; character definitions and appearance choices under `content.characters`; items under `content.items`; spells under `content.magic`; monsters and battles under `content.combat`; and shops and treasures under `content.economy`. Callers navigate to the owning catalog instead of asking `RealmzContent` to forward feature lookups. Portable item and spell identities therefore resolve against the same active application-plus-scenario catalogs used during package validation.

Cross-reference validation proceeds in authored dependency order: rule catalogs, Simple Encounters, Thief and Complex Encounters, then program instructions and destinations. Installation first recognizes a validated immutable target. Otherwise it reads the source once, hashes those bytes, writes them to an app-owned staging file checked byte for byte, and validates that staged copy; a new target is the staged copy renamed atomically, receipted with the in-memory hash, and only then cached. An occupied target is receipted only when it still hashes to bytes that validation read, so a file swapped between validation and hashing cannot inherit trust. The disposable receipt includes the exact application package hash used for effective validation, so replacing the stock library invalidates prior trust without migrating the scenario archive or a player save.

The known format-v2/decoder-6 receipt predates application-library binding. It may be refreshed only after its exact shape, current schema, file identity, and recorded archive SHA-256 pass, followed by complete untrusted package validation. Old cached graphs and document images never cross that boundary. Unsupported receipt versions and incompatible scenario content still fail explicitly; install a current scenario revision rather than rewriting its archive or weakening validation.

Package loading is startup-sensitive. Preserve receipt checks, parsed-document sidecars, bounded graph caching, and background installation. Run `tests/infrastructure/test_package_repository.gd` for decoder or validation work, `tests/infrastructure/test_package_install_task.gd` for worker lifecycle, and the full verification gate before changing a package contract.

The same worker first obtains a `ScenarioSetupCatalog` through `PackageSetupReader`. It decodes only campaign restrictions, effective creation/admission rules, appearance references and party choices; world and program construction continue afterward. Compact setup documents are bound to the source archive, schema/decoder and application identities, and compared with hash-verified archive content before use. Generate the thirteen adjacent bundled catalogs with `godot --headless --path . --script res://tools/generate_setup_catalogs.gd`; append `-- --check` to verify exact reproducibility. The aggregate verifier includes that check. These disposable caches never replace full package validation or alter package bytes.

For imported schema v7, `PackageClassicRecordDecoder` retains typed presence and source facts separately from operational usability. `PackageClassicRecordBinding` checks complete native records, programs and player maps against their compiled definitions and retained effective bytes. `PackageClassicRuleSelectionBinding` verifies the original source-set commitment, explicit Race/Caste source choices and full effective wire-row digests. Setup retains only the native source inventory and rule-selection subset and applies the same rule and NI/Spell ownership checks before publishing a party catalog. It never copies the full program graph into a setup cache. V7 scenario item slots 800–999 resolve only against native scenario definitions; standalone application placeholders remain available for bootstrap and legacy packages.
