# Classic functional differential

Classic-visible behavior is developed through a rolling differential gate. Current Remake identifies existing functionality, mappings, tests, and likely differences. Castle source controls the behavioral decision; a controlled Castle runtime fixture is used only when complete source flow is insufficient. Providence must preserve the authored inputs, and Realmz Remake 2.0 must own the result through typed runtime boundaries.

Media ownership follows Castle's application/scenario split. Realmz Rebuilt ships versioned integrated resource families, beginning with all 142 `snd ` resources from the pinned `The Family Jewels` fork. Providence emits scenario-owned media and exact overrides rather than copying the integrated bank into every package. The runtime's composed catalog checks the scenario package first, then the application catalog; an ambiguous package key fails instead of falling through. PICT and CICN migration remains family-specific while those workflows still require package asset IDs.

The machine-readable record is `tests/fixtures/oracle/classic-functional-differential.json`. It contains the detailed paths, symbols, commits, expected traces, tests, decision state, and links to the application workflows those cases support. This document summarizes only the current conclusions.

Differential cases provide depth for behavior already investigated; they are not the completeness denominator or the default scheduler. The fixed denominator and parity-convergence batch live in `tests/fixtures/oracle/classic-application-workflow-inventory.json`. Its deterministic [status report](classic-application-workflow-status.md) separates complete-application gaps from route coverage, individual opcode ownership, and modern host work. A functional workflow receives more differential archaeology only when ordinary play exposes a discrepancy, a reachable blocker or high-risk boundary depends on it, Providence may lose authored data, or source ambiguity affects a target campaign. Every differential case and workflow link is validated bidirectionally.

The current combat-command tranche separates Auto Turn from saved character Auto and derives all command availability in core rules. Auto retains Castle's Bandage-before-Turn-Undead priority, tagged RNG, toggle/button sounds, mandatory-interaction stops, immediate removal from a defeated combatant, and one transactional operation limit. Delay and manual Bandage expose two source defects rather than silently copying them: `FD-COMBAT-012` prevents a last-slot Delay from immediately selecting the same actor, and `FD-COMBAT-013` restricts Bandage to one actual living bleeding recipient. Round progression preserves the party-ordered bleeding ticks and Castle's default second warning-sound draw after individual survivor sounds. Turn Undead preserves source-order targets, the signed `canSummon` exclusion, threshold and experience formulas, eight-frame effect identity, death-macro boundary, and once-per-battle state. These five workflows are functional from synthetic evidence; ordinary AOGM acceptance remains the current certification target. The follow-on Undo slice records only actor, activation-start cell, round, cursor, and availability. Result-free movement may be undone after save restoration; attacks, reactions, spell/item results, or turn advancement close the boundary. `FD-COMBAT-014` rejects Castle's unchecked occupied-cell overwrite. Repeated Undo and initiative-edge re-entry remain unresolved until controlled Castle runtime fixtures exist.
