# Deterministic playthrough orchestration contract

## Purpose

Own the pure transaction coordinator that joins Realmz game state and rules to the scenario VM without making either lower layer depend on the other.

## Ownership

- `GameSession` public operations, transaction checkpoints, exact-once commit, request identity, revision, and aggregate lifetime.
- `session/` owns `SessionSnapshot`, the small `SessionContinuation` envelope, strict decoding, transaction result vocabulary, restore admission, and detached view projection. Feature-owned continuation payloads and factories remain under `continuations/` until their owning feature migration.
- `SessionRestoreValidator` is the restore transaction entry point and validates session continuations through named confirmation, item-target, learned-spell-target, and scroll-target families. `SessionRestoreStateValidator` validates detached game truth, and `SessionScenarioRestoreValidator` validates pending VM workflows. Together they construct one detached typed restore candidate; `GameSession.restore` alone commits it to the live aggregate, so every failed validation leaves the current session untouched.
- `SessionInteractionFactory` is the single owner of session-level request reconstruction shared by live orchestration and restore validation.
- Session workflow contexts and feature services for lifecycle, exploration, inventory/magic/services, combat/rewards, and application hooks.
- `SessionContext` owns initialization, restore assignment, snapshot construction, and the current content, state, deterministic RNG, rules, VM, Scenario Action state, runtime API, continuations, pending session interaction, and revision. Internal intent, exploration, scenario, response, and debug coordinators share that one context while leaving transaction commit and rollback in `GameSession`.
- `SessionIntentCoordinator` dispatches each already-validated player intent to its named workflow or coordinator. Coordinators construct rejected, committed-failure, waiting, completed, and close outcomes through `SessionCoordinatorResult`, which owns that result vocabulary; `SessionContext` does not forward those constructors. Coordinators never advance the session revision themselves.
- `SessionDebugCoordinator` routes developer commands across workflow, combat, and scenario owners while `GameSession` retains the final transaction commit and unsaveable-operation flag.
- The standalone character-creation session adapter.

## Local Contracts

- Each typed `SessionContinuation` body implements the public `wire_payload` codec operation used by the owning envelope. Continuation callers use typed accessors and never invoke body-private serialization helpers.
- This layer may depend on `src/game` and `src/scenarios`; neither lower layer may depend on `src/playthrough`.
- All classes are pure `RefCounted` or value-like data. They never retain Nodes, repositories, presenters, or the owning application.
- Workflow services receive an explicit ephemeral `SessionWorkflowContext`; they never retain the owning `GameSession`.
- `GameSession` owns one `SessionContext` and names its content, state, RNG, VM, continuation, interaction, and revision capabilities directly; it never mirrors or copies coordinator state. Operation-scoped coordinators receive the same context by reference, expose only named collaboration operations, and construct their typed outcomes through `SessionCoordinatorResult`. `GameSession` releases the short-lived coordinator graph after each operation and alone advances revision, commits, rolls back, closes, and constructs the public `SessionStep`.
- Exploration operations have direct workflow owners: `ExplorationMovementWorkflow` owns heading, fatigue admission, boats, and movement commits; `ExplorationSearchWorkflow` owns Search mode and secret checks; `ExplorationTimeWorkflow` owns Camp, Rest, and field Heal; `ExplorationContinuationWorkflow` owns post-clock/post-move continuation construction and validation; and `LocationNoteWorkflow` owns player-authored map notes. `SessionIntentCoordinator` selects the operation, `SessionExplorationCoordinator` owns resumption, and `GameSession` commits the returned result. At fatigue 135, movement commits only exact Castle warning 54 before heading, wealth, camp, topology, time, or RNG work; Castle's land-only exception remains when the scenario has disabled camping, preventing an unrecoverable soft lock. The opcode-69 character-spellcasting flag is checked before field Heal begins: blocked Heal commits only Castle warning 113 as a sounded application notification and changes no clock, RNG, stamina, spell points, or fatigue.
- A rejected intent is distinct from a failed transaction. `SessionCoordinatorResult.rejected` preserves the current revision for validation or rules rejection before a transaction begins; a committed failure advances revision and retains its ordered events.
- `GameSession` alone owns rollback, request matching, revision changes, and exact-once commit.
- `GameSession` records the current map's bounded topology-visible cells into exact save-owned sight memory only after start/restore and at successful completed or waiting transaction boundaries. Failed or rolled-back operations cannot reveal cells; detached projection remains read-only.
- Boat boarding and third-attempt shore disembarkation are typed `YES_NO` interactions owned by a `boat-choice` continuation. Response coordination re-probes the same source/destination and boat state before mutation; accepted, declined, saved, and restored paths apply sound, time, overlay, movement, and post-time continuation exactly once.
- Post-AP coordination ignores a Classic header destination equal to the issuing AP's source cell before comparing it with the party's live location, so an in-program teleport is never undone by a source-self header.
- Post-AP coordination also suppresses every issuing header destination when opcode 70 restored the saved party position during that AP. The committed restore event is the sole suppression fact; save mode and unrelated teleports retain ordinary header behavior.
- Post-move AP selection treats immutable `active` as the initial gate. A serialized opcode-13 chance override supersedes that gate, allowing Providence-packaged inactive placed records to become eligible while nonpositive chances and explicit one-shot disablement still stop execution without falling through to later same-cell records.
- Random-battle coordination passes both authored endpoints through `RealmzRng.draw_between_classic`; inverted endpoints remain legal when Castle's signed-short scaling can resolve every selectable battle. It never sorts or normalizes the package record.
- A selected Classic Choice mode-zero backout or authored Simple/Complex Encounter cancellation is applied only by an active post-move AP continuation. On land it reverses the exact committed movement vector; in every map kind it preserves the issuing trigger, skips header destination and random-region handling, and consumes no additional gameplay time or RNG.
- Restore validation recomputes a pending Pick Lock preview from the saved session RNG and authored thief record. It rejects forged frames, thresholds, cadence, deadline, character/action identity, or mutable encounter flags before constructing the replacement VM.
- Restore validation admits staged random-power combat items only when the active party actor still owns the usable authored-power-eight item and its executable spell. A pending VM combat request is regenerated from detached authoritative state and must match the saved typed request exactly, including the rolled power and target surface.
- Restore validation admits save-owned shop buyback stock only when every quantity has one unique native slot in the item's 200-slot band and that slot does not collide with active immutable stock. The quantity and slot maps are one strict save contract and must restore together.
- Restore validation must never mutate the live session. Candidate state, rules, RNG, VM, continuations, and interaction are replacement objects until the final `GameSession` assignment block.
- Scenario-mediated and direct player operations must converge on the same game rules and playthrough implementations.
- Dictionaries are permitted only while crossing an explicit package/save/event codec. Live workflow state and continuations are typed.
- Every continuation body and nested scenario handoff must reject unknown fields and versions, detach mutable values, and round-trip through its strict wire codec before entering a snapshot.
- Post-clock exploration admits explicit attempt-search completion kinds for blocked and successful land movement. They carry no direction, survive strict save validation, run the ordinary secret check exactly once, and then converge on the existing completed or post-move path.
- A direct door-item XAP owns a typed `item-xap` continuation containing the exact character, instance, immutable item, program, and optional source battle identity. It spends the validated charge before VM dispatch, restores game state, RNG, VM, and Scenario Action state together on failure, survives save/restore and Party Death handoff, and returns to the same active battle without rerunning the item opcode.
- Field spell, scroll, and charged-item targeting rebuild the pending request from the typed targeting continuation during restore. Detached projection and restore legality consult `ClassicSpellDispositionRules` and its named structural rules owners rather than duplicating special-ID allowlists. The reconstructed request must retain the exact selected power, source-authored spell display facts, stable actor identities, and any ordered summon-anchor coordinates required by the owning workflow. The field-invalid scroll Discard/Keep interaction is a distinct typed continuation that restores only when the exact character, equipped case, slot, spell, and power still match; acceptance clears one slot and decline commits no gameplay mutation.
- Detached views are cached by committed session revision. The projector defaults to a 25×25 map window for headless consumers, while the host may request its current visible cell span plus a bounded presentation-only guard; changing that span invalidates only detached read-model caches and neither advances the revision nor mutates state. Copy-on-write `MapWindowView` patches must preserve typed 8×8 chunk storage when a replacement enters a previously absent chunk, and every earlier detached snapshot remains immutable. The projector may reuse immutable domain projections only for a strictly recognized ordinary adjacent movement/time event sequence and emits a typed, nonserialized viewport/visibility delta for that revision. LOS movement retains a complete current map projection while identifying and rebuilding its changed visibility edge, reusing unchanged map cells and non-map domains through the ordinary exploration shell; every unknown, interaction-changing, map-changing, restore, or combat event invalidates that conservative fast path. Domain revisions let presenters update only affected visible regions without changing simulation state or save shape.
- Detached projection builds the Bestiary from the selected monster set's ordered menu-visible definitions, not from current allies or combat discovery. It carries authored descriptions and immutable combat facts without adding Bestiary state to the save.
- The projector constructs Race/Caste setup records from immutable typed definitions, including source-backed rule facts and empty authored descriptions as empty values. Presentation never reaches back into package content to calculate these records.
- Direct-session combat remains intent-driven rather than fabricating a scenario continuation. `GameSession.view()` attaches the same runtime-projected typed combat command contract used by scenario battles whenever combat is active and no mandatory interaction owns the surface.
- A manual move into an eligible same-allegiance battlefield actor opens the save-owned `combat-friendly-collision` choice. Restore revalidates the battle, active actor, adjacent size-zero ally, destination, and movement threshold before Swap Positions or Attack Friend resumes the shared combat-reaction transaction exactly once; Party Auto bypasses this player choice through the rules-owned swap branch.
- `GameSession.apply_debug_command` is the typed developer-command boundary used only by the debug host. It validates a committed session boundary and routes topology warp, adjacent no-clip, party restoration, encounter launch, battle launch, and forced victory through their ordinary transaction owners. No-clip alone bypasses cell/feature admission without advancing time or RNG, never leaves the current map, and emits a strict adjacent event eligible for incremental detached projection. Party restoration is legal at an active combat request without replacing that request or advancing its VM frame. Forced victory is also legal there, but must complete the issuing Classic or Safe combat continuation through ordinary ally, reward, after-battle, and exact-once VM return handling; a failed handoff rolls game state, RNG, and VM state back together. Every other command retains its ordinary committed-boundary requirement. A debug encounter's ephemeral VM program is intentionally unsaveable; `snapshot()` returns null until that interaction closes.
