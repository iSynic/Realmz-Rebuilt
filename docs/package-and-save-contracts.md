# Package and save contracts

## `.realmz2`

A deterministic ZIP contains canonical minified JSON and content-addressed media:

- `manifest.json`: format/version, campaign/content IDs, compiler provenance, engine requirements, start location, capability inventory, file hashes, package hash.
- `content.json`: Realmz definitions and text.
- `world.json`: maps, authoritative topology, APs/XAPs, transitions, random rectangles, timed encounters, and immutable metadata.
- `scenario.json`: Classic instructions, Scenario Action programs, state definitions, and migrations.
- `assets/index.json` plus hashed media payloads.

Providence owns the schema. The runtime mirror under `contracts` is byte-identical and independently enforced. The package excludes editor layout, absolute paths, compatibility annexes and archaeology artifacts. Retained native source payloads and their exact source indexes are immutable package content; Providence alone decodes them into production typed records. Rebuilt does not introduce a second native parser into gameplay.

Realmz application content and scenario content are separate authorities. Rebuilt ships the complete stock Realmz library once: rules records, strings, fonts, controls, integrated media, and other application resources. A campaign package contains only scenario-owned records/media and normalized references to stock identities. At load time Rebuilt requires the package and application library to share `rulesVersion`, clones the immutable application definition tables, then overlays scenario definitions by exact stable ID before validating references. A package may therefore replace an exact application definition or resource only where Castle's scenario-before-application lookup supports it; every unmentioned stock definition remains application-owned. Providence validates those references against the pinned Rebuilt application contract and does not duplicate the application item or spell catalog into campaign output. Shared Race/Caste tables may be omitted, while scenario-authored tables remain packaged overlays.

Canonical JSON documents and source-only native payloads are Deflate-compressed in the ZIP; operational media retains its existing encoding. Exact shared native/media payloads have one physical entry using the operational asset's existing choice. Compression changes archive bytes and provenance hashes but not canonical document bytes, manifest package hashes, or runtime meaning.

Schemas v3 through v7 are supported runtime contracts; each package must match its exact mirrored schema hash. V4 preserves imported native monster values outside v3 ranges, and v5 preserves incomplete EDCD tails with prepared consumer guards. V6 additionally requires one signed-16-bit `classicTileValues` entry per map cell in logical row-major order. These runtime facts preserve Castle marker bands independently of normalized terrain and colocated AP records; older schemas reject the field and retain their existing compiled interpretation. Corrected bundled baselines carry new package identities, while installed prior revisions and their bound saves remain unchanged. Third-party scenarios receive the corrected compiler output through explicit reimport. See [Classic scenario imports](classic-scenario-import.md) for their deferred-reference rules. V7 additionally preserves fixed native slots, complete and partial record presence, signed fields and uninterpreted source spans independently of consumer usability. Its semantic save updates are exact pinned transitions, with the then-current save v5 and Character Files v2 unchanged; current writing is v6 and reading supports v5/v6; see [faithful records](faithful-scenario-records.md). The following v3 description is historical and retains that version's index meanings. The mirrored schema is SHA-256 `05ced7b000683f53e6220b9ac8f7d41c801e7e2c78c874287c2ae694b585273d` from Providence commit `9b037e5d6436a970eeeaaebea7a70c6867e89e99`. Manifests use format version 2 and all five canonical documents use schema version 3. Versions 1 and 2 are rejected explicitly and must be re-exported; no runtime adapter or defaulting branch survives the cutover. V3 retains the normalized display, rules, encounter, topology, media, and application-hook data established by the unpublished v2 contract, makes runtime-required values compiler-owned inputs, and preserves Battle `distance` as an initial-placement field rather than a weapon requirement. Monster records preserve independent Classic name identity plus authored bestiary description/menu visibility. Maps preserve nullable base scale and the compact-cell forest semantic. Each occupied shop record preserves its unique native slot so category order and first-empty buyback placement remain deterministic save-owned behavior. Scenario-owned Custom 1–3 audio declares its independent slot. Opcode 92 alone carries ten operands compiled from two consecutive Extra Code rows; ordinary actions retain five. Timed records carry an exact `classicMacroId` and matching `xap:<id>` program reference because Castle dispatches Data ED3 directly; they do not masquerade as placed AP record indexes. Providence emits canonical `Land level N` and `Dungeon level N` playable-level names while preserving authored STR# player-map titles on player-map records only. Providence's canonical project and native compatibility annex remain outside the package. Canonical schema bytes use LF line endings so the compiler and runtime hash the same contract on Windows.

The schema-v3 world contract uses Providence's fixed row-major `realmz2.compact-cell-rows.v2` topology ABI. Castle's packed dungeon fields and Providence's Layout record remain compiler inputs, not runtime map models. Each compact cell tuple carries semantic flags, ordered directional edges/features, trigger and random-region references, base/overlay render identities, exact Classic `needboad`, and blocked-attempt timeclicks without repeating map IDs, coordinates, or JSON property names across 90×90 maps. Each land map also carries the active landlook's exact tile-60 removed-boat and tile-147 placed-boat profiles; dungeon maps require `null`. Runtime topology decodes cells lazily and applies session-owned boat-presence overlays through those immutable profiles, so movement, LOS, rendering, save restoration, and battlefield derivation see the same effective cell. Placed AP references compile in native record order and retain `classicRecordIndex`; duplicate record identities on one map fail validation. Placed AP headers compile to a typed `postActionLocation`; XAPs use `null`, and tile mutation remains an explicit scenario instruction. Random rectangles retain signed 1-in-10,000 chances, battle ranges, three random-door slots, only/option behavior, and media IDs. Its content contract carries direct Simple/Complex/Thief/Timed Encounter records, a distinct Classic option-label table, and direct race, caste, item, spell, monster, battle, treasure, and shop definitions. The base monster catalog represents Normal Monsters; optional typed sets `-1` and `1` contain complete reachable replacements from Data MD-1 and Data MD1 with unique stable identities. A package may not emit a partial set or ambiguous replacement. The application library owns 799 nonzero standard Classic items plus stock supply identities; scenario item records are emitted only when they are scenario-owned additions or exact-ID replacements. Standard Data S records belong to the application library; custom Data Spell slot 0 is packed ID 5101 and slot 104 is 5715. Monster weapon restrictions retain the signed Data MD byte as `requiredWeapon`; `magicToHit` is its independent weapon-plus threshold. Battle records retain their unrelated placement `distance`, explicit monster slots, coordinates, and traitor inversion. Its scenario contract contains trigger/program references, exact application-hook program IDs, preserved `ClassicAction` instructions, typed `CallScenarioAction` instructions, compiled Safe bytecode, versioned action-state definitions, and migrations. It does not contain Safe visual/source AST, behavior anchors, authoring modes, or sandbox source.

For every package with a reachable battle, `world.json` now carries immutable `battleTerrainSets` and each map identifies its effective set. A land set contains its active landlook records 0 through 200 followed by shared `Combat Data BD` records 201 through 400; the active landlook therefore wins Castle's overlapping tile 200 exactly once. The dungeon set contains shared records 200 through 400. Every tile retains signed sound, time, solid, boat, and forest values, exact boolean flags, and the 3×3 `combatBuild`; incomplete ranges or malformed builds fail both export and runtime construction. These are immutable construction inputs, not an alternate exploration topology. Tactical positions, battlefield generation, proximity-gated melee, and Guard/withdrawal reactions use session-owned combat geometry and serialized cursors. Ranged attacks remain disabled until projectile range, costs, and resolution are source-owned.

Managed Providence media and decoded imported scenario resource-catalog pictures/icons/sounds become content-addressed package payloads. Classic resource identity is the exact four-character type plus signed ID; case and trailing spaces are significant, and equal numbers in `PICT`, `cicn`, and `snd ` are unrelated resources. Scenario-managed media replaces the imported scenario-catalog entry for the same key. Realmz's integrated `snd ` bank is versioned application media and is not copied into every campaign; a packaged exact sound key is an explicit scenario override and resolves before the application fallback. Package ambiguity never falls through to a plausible built-in resource. Missing integrated media is a Realmz Rebuilt build/install defect, not a campaign-readiness defect. This deterministic composition preserves Castle's normal scenario-before-application result without exposing its mutable global resource-file cursor. Providence and the runtime independently reject duplicate package asset IDs and exact package resource keys. Application PICT/CICN migration remains resource-family-specific because current map, appearance, and battle contracts still carry package asset IDs. Every referenced map tileset is a required content-addressed PNG with explicit grid metadata; Providence normalizes Classic PICT 302's fixed dungeon-composition region to a 4×4 runtime atlas and, for reachable battles, emits the complete 20×20 image as the exact `classic-battle-tiles-302` battle atlas. Castle's effective combat graphics combine the active landlook for battle tile IDs 1–200 with that shared atlas for IDs 201–400. Classic positive and negative icon-backed land values compile as the landlook's base terrain plus an exact packaged `cicn` overlay when the scenario owns that resource, or a normalized application-CICN reference otherwise; neither form may masquerade as a tileset index. Absolute paths and resource-fork bytes never enter the package.

The complete pinned-source audit for the 13 bundled scenarios restores 515 previously omitted scenario-owned CICN descriptors, including 67 in Half Truth and both authored monster-facing identities. It records one preserved duplicate-key ambiguity in Twin Sands of Time, with no undecodable or mismatched decoded resources. Descriptor identity remains distinct from content addressing, so equal image bytes share one payload without losing either exact resource key. Trouble in the Sword Lands also reconnects two positive CICN land cells to their scenario overlay while retaining the landlook's base-terrain profile. These rebuilt archives intentionally receive new package hashes; installed packages and package-bound saves are neither rewritten nor admitted through a compatibility bypass.

Every package also carries the complete selectable Classic character appearance catalogs: portrait `cicn` 257–376 and tactical `cicn` 9000–9119. Each effective entry has an explicit `portrait` or `combat-icon` role, stable asset identity, decoded PNG dimensions, and ordinary exact-key precedence. Providence and the runtime both reject a missing, duplicate, wrongly typed, or undecodable entry. Castle's Human Data Race value stores portrait set zero even though the browseable Portraits fork starts at 257; `FD-CHARACTER-002` deliberately aliases set zero to the first real six-image set rather than requesting unavailable `cicn` 251–256.

For strict authored packages, `PackageRepository` rejects unsafe/extra entries, noncanonical entry order, schema or capability drift, per-file size/hash mismatches, package-hash mismatches, malformed topology, duplicate identities, incomplete character appearance catalogs, unresolved map/trigger/program/action references, unsupported Classic opcodes, invalid Scenario Action namespaces or callers, argument/type mismatches, oversized Safe programs/arrays, and unknown capabilities before constructing `RealmzContent`. `realmz.scenario.gdscript-actions-v1` is a recognized but unavailable capability and fails readiness until an OS-confined external host exists.

Installed-package discovery is deliberately staged. It verifies manifest/schema/capability metadata and deterministic inventory without parsing topology or constructing campaigns merely to draw the library. Generic discovery retains every immutable content-hash revision for diagnostics; the campaign selector groups valid revisions by campaign ID and exposes the most recently installed file only. The application also discovers the exact provenance-pinned 13-scenario Castle bundle from immutable release resources, then overlays valid user-installed revisions by campaign ID. Selecting a bundled baseline runs the ordinary complete validation and installs the exact bytes under `user://packages`; bundled scenario location is not a trusted-package shortcut. Importing any external `.realmz2` follows that same integrity and typed-validation path, copies the exact bytes transactionally, and writes a durable app-owned receipt containing its compressed archive hash and immutable file identity. Subsequent Play operations verify the receipt's byte count and modification identity plus schema/campaign/package manifest identity before constructing Providence's compact typed content; they do not rehash the archive, rehash every ZIP payload, or repeat compiler-level media/reference validation. If the installed archive changes, the receipt is invalid and the package must be reinstalled. An in-process typed cache remains an additional optimization, never the only trust record.

## Third-party scenario policy

Every scenario Providence can import must remain exportable, including alternate versions, unfinished scenarios, and authored defects. Import/export eligibility never depends on a known source hash, approved title, clean gameplay audit, or completed campaign. Hashes retain integrity, provenance, deduplication, revision identity, and exact save-binding roles.

Imported deferred-reference packages preserve unavailable authored targets and unknown native instructions through the versioned compiler/runtime representation. Structural decoding, package encoding, integrity, and resource limits remain mandatory. Known Castle defaults and unmatched-opcode fallthrough are explicit behavior; an unimplemented operation or incomplete operand read has a prepared diagnostic at the consuming execution boundary. Do not discard authored records, invent replacements, or claim that admission or a guarded error establishes Castle parity.

Import/export, installation, starting, exercised behavior, and campaign completion are separate outcomes. The [import contract](classic-scenario-import.md) owns the current implementation and evidence; [ADR 0019](adr/0019-third-party-scenario-availability.md) retains the availability decision.
## `.r2save`

Saves write v7 and strictly read v5-v7. V7 differs from v6 only in its VM snapshot schema 4: type-tagged frame values and `nativeInvocationBegun` instead of a step count (ADRs 0026 and 0027); v5/v6 files must carry VM schema 2/3. V6 preserves exact signed clock components and explicit timer/combat/VM execution facts, including one shared native destination/selected AP, invocation guards and nullable captured GOSUB return headers. V5 decodes its recorded minute total and legacy facts without replaying history. Loading never rewrites a file; the next explicit write uses v6. Older builds reject v6 while preserved v5 originals and backups remain available. See [ADR 0025](adr/0025-exact-clock-and-save-v6.md). A versioned envelope under `user://saves/<campaign-id>/` records campaign/package identity, rules and fidelity decisions, and one detached `SessionSnapshot`. The snapshot contains complete `GameState`, authoritative equipped-instance order, overlays, clock, mutable economy—including base-shop quantity overrides and paired buyback quantity/native-slot maps—combat and reward state, scenario replacements, VM frames, Scenario Action state, RNG state and draw count, pending interaction, and the exact session continuation needed to resume the committed boundary. Presentation state and the bounded debug RNG trace are never saved.

Every closed protocol variant—including intent payloads where persisted, interaction requests and responses, VM/session continuations, and nested workflow state—encodes as `{kind, version, data}`. Its codec requires the exact fields for that kind and rejects unknown kinds, versions, or fields before constructing a session. JSON dictionaries remain inside the infrastructure codec; `GameSession`, core workflows, and scenario code receive typed values only.

Versions 1 through 4 are intentionally incompatible. They are reported to the user as belonging to an older Realmz Rebuilt save contract and are never migrated or partially interpreted. There is no Classic or prior-Remake save importer.

Update Save can create a verified current-format copy for each of the thirteen stock packages immediately preceding the native map-marker correction. The bundled provenance catalog and hash-pinned correction receipt identify the exact old/current pairs. The operation verifies both archives, the original installation receipt and application library, unchanged media and unrelated payloads, and reversal of only the declared marker/document changes. It then restores the complete saved state against the corrected package without executing gameplay and requires unchanged gameplay, RNG and continuations before publishing and reading back a separate copy. Selected artwork and the map thumbnail travel unchanged. The original archive, primary save, backup, active adventure and Quick Save target remain untouched; an identical retry may reuse the verified copy, while a different destination is never overwritten. Earlier event results remain recorded rather than being reset or replayed.

Trouble also offers Update Save from its immediately preceding schema-v6 bundle to the exact native XAP 330 restoration. The byte-pinned `trouble-payment-restoration.json` receipt permits only that added refusal program; every existing program and unrelated payload remains unchanged. Its original pre-marker revision can take the existing marker update with the same addition explicitly reversed before comparison. Both paths preserve all saved state and publish a separate copy; they do not replay an earlier failed purchase or clear a saved runtime fault.

The three exact additive revisions in [bundled shop restoration](bundled-shop-restoration.md) and the separately pinned Half Truth media transition retain their existing admission rules. Earlier stock revisions, imported scenarios, and save v1-v4 do not qualify for the marker correction. Missing original-package evidence produces guidance to restore or validate the retained installation; no general package-hash bypass or automatic update exists.

Maintainers can exercise all thirteen transitions with retained pre-correction archives and a new scratch directory, without accessing player saves:

```text
godot --headless --path . --script res://tools/marker_save_update_probe.gd -- <retained-original-directory> <new-absolute-scratch-directory>
```

Saving is allowed only at committed session boundaries, including party setup with a partial party. Infrastructure writes a temporary file, decodes and validates it through the strict v6 codec, rotates one backup, and atomically replaces the slot. Restore validates a complete replacement—content identities, equipped-instance order, carried-load totals, shop slot bands and collisions, requests, continuations, VM state, combat ownership, and RNG position—before changing the active session. Failure leaves the current session untouched.

## Portable imported character art

Save v6, legacy-readable v5 and Character Files v2 support an optional `characterArt` array containing exactly the imported portrait/icon identities selected by their party, character or creation draft. Each entry has `id`, `kind`, `group`, `label` and base64 `png`; IDs bind the role and PNG SHA-256. Storage rejects duplicates, wrong roles, missing or extra selected assets, invalid PNGs, mismatched hashes, oversized payloads, and nonnative dimensions (44×44 portraits, 32×32 player icons). The pure snapshot and existing character codec retain only appearance IDs. No file path, image, group label or library preference enters gameplay state. Stock-only records omit this extension and preserve their existing wire shape. See [ADR 0021](adr/0021-portable-character-art.md).

## Saved-party transfer

Scenario-specific race/caste gameplay definitions scope a character to its source campaign. Character Files and saved-party admission reject other campaigns even when IDs and definitions coincide; compatible revisions of the same campaign remain eligible. Scenario-owned rows identical to normalized application gameplay definitions do not restrict stock characters; creation eligibility and default artwork are excluded. Stock-source characters use destination definitions without a fingerprint-equality gate, following Castle admission. Custom-source campaign confinement is an explicit Rebuilt policy, independent of Castle's character-export cleanup.

Importing a party from a saved adventure reads and validates the source save against its exact installed package revision before exposing characters. A missing revision must be installed explicitly; another revision with the same campaign ID cannot substitute. The review is bound to the source file hash, source package hash, destination package hash, and current setup revision. If the source changes or setup moves on, the host refreshes or rebuilds the review before accepting a selection. The workflow rechecks capacity and character admission on detached copies, then commits the selection together; it never mutates the source save or writes imported characters back implicitly.

Each candidate preserves its stable character and item-instance identities. Definitions, resources, and scenario-owned items or spells that do not match the destination are omitted with a review reason; a character is rejected when incompatible equipped effects cannot be removed safely. The destination recomputes carried load and admission from its own rules and catalogs. Source-owned pooled and banked wealth, shared storage, confiscated equipment, recruited allies or summons, and battlefield drops stay behind. Party transfer is a new-adventure operation, not save migration or package-hash rebinding.

## `.r2char`

Reusable character revisions are separate from `.r2save`. A record contains a stable character ID, immutable revision hash, rules version, source campaign/package provenance, publication metadata, complete detached character state, inventory/spells, and source revision. `CharacterVaultRepository` stores revisions under `user://characters/<character-id>/`, validates the requested character and revision identities on every read, retains one recoverable backup, and archives instead of deleting. The host exposes current and earlier immutable revisions, exact target-campaign eligibility, archive confirmation, and recovery without allowing presentation to touch files. Import is a typed session intent; eligibility failures identify missing definitions, restrictions, level limits, unavailable/wrong-role portrait and combat-icon IDs, or an exact item-instance ID already owned by the assembled party. The session never rewrites a conflicting instance identity: it rejects the import before mutation, and aggregate restore enforces the same one-owner invariant across inventories, party storage, equipment escrow, and combat fumble custody. The session recomputes personal carried load from the target package's immutable item weights and the imported wealth rather than trusting a stale revision total; an over-limit result is ineligible without stripping or substituting content. Finalizing a newly created character yields a typed, saveable publication confirmation. Acceptance publishes only after the session has committed the character and cleared the interaction; decline has no repository side effect. Ordinary campaign changes never write back implicitly.

New Character Files v2 also carry optional `sourceRules` version 1: exactly the race/class IDs, their normalized SHA-256 fingerprints, and captured custom-scope booleans. The revision digest binds the complete extension to the existing source provenance and character. Unknown fields/versions, malformed hashes, mismatched selected IDs, or custom scope without a source campaign reject. This is definition identity, not an executable payload or a replacement campaign. Legacy v2 records without it remain readable through exact source-package validation; unresolved provenance is never guessed. A full backup plus explicit, source-verified publication of new revisions can repair old provenance without modifying original revisions. See [ADR 0022](adr/0022-portable-character-rule-identity.md).

The explicit Repair Character Files action is limited to current-format current revisions. It accepts the exact source catalog named by provenance or one of the four pinned stock-only historical profiles listed in ADR 0022. It requires review before writing and a complete hash-verified backup of the vault, including history, archives, and invalid files. A joined worker copies original envelope and state fields into separately hashed revisions with validated `sourceRules`; it preserves custom flags and never changes saves or the active party. Unavailable evidence is skipped with guidance; v1 records are not migrated. Index readback and per-record rollback are required. Failure restores touched current-index selections; any verified new revision already written remains as noncurrent history. If interrupted, a subset of repaired revisions may remain current beside the complete backup; a later explicit repair can resume. This is per-record recoverable behavior, not a global crash-atomic transaction. The workspace, backup, and completion UI contract includes Open backup and a visible Done action; implementation verification remains pending.

Character Files v2 store the same authoritative equipped-instance order as saves v5-v7. Character Files v1 is intentionally incompatible and is reported without migration, overwrite, or deletion. Character revision storage remains independent from saves: `SaveRepository` owns the v6-write/v5-v6-read envelope transaction, while `CharacterVaultRepository` owns validated immutable `.r2char` revisions and their separate compatibility rules.
