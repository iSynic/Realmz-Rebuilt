# Scenario runtime

Compiled scenario definitions are immutable game content. `RealmzContent.scenario` is the program graph, while `RealmzContent.scenario_records` exposes `ScenarioContentCatalog` for messages, option labels, triggers, and direct encounter definitions. `ScenarioVm` executes instruction timelines, while `RealmzRuntimeApi` adapts Classic instructions and safe scenario operations to public rules and playthrough collaborators. Scenario Actions are reusable callable programs; call sites do not contain executable gap behavior.

`ScenarioClassicControlFlow` is the readable directory for Classic frame changes: XAP/program branches, GOSUB installation, Simple/Complex Encounter entry, result/repeat loops, and encounter exit. It mutates the VM's typed frame array and returns a `ScenarioDirectiveTransition`; `ScenarioVm` remains the owner of pacing, interaction suspension, trace limits, frame return, halt, and snapshots. This keeps Classic control flow out of the central execution loop without introducing a second VM state.

Mutable scenario truth does not live in the VM or in an undifferentiated `GameState` dictionary. `ScenarioProgressState` owns searched cells, quest values, journal discovery, and source-ordered selected characters. Its `ScenarioEncounterState` owns timed encounter overrides, eliminated choices and results, attempt counts, thief flags, and program redirects. Both remain pure game state and write the existing flat save fields, so this readable in-memory boundary does not change save representation.

Keep dictionaries at package and save codecs. `ScenarioRuntimeContinuation` is only the stable versioned envelope for a suspended operation. Interaction, age, service, combat, and reward code construct the corresponding typed body through the feature factories in `src/scenarios/runtime/continuations`; `ScenarioRuntimeContinuationCodec` alone accepts their dictionary representation. Begin with `tests/scenario/test_scenario_vm.gd`, which protects all 34 stable wire kinds; reward and battle-return behavior is owned by `test_reward_workflow.gd`. Castle evidence explains behavior but does not become a second host architecture.

VM frames and program transfers carry `ScenarioExecutionContext`, the live typed provenance for triggers, encounters, application hooks, battles, and program transfers. Ordinary frame copies stay typed. Only `ScenarioExecutionContextCodec` translates that value to or from its sparse save dictionary, so adding provenance has one obvious wire owner and cannot quietly reopen dictionary-driven execution.

Service opcodes enter through `ClassicServiceOperations`. Shop and Temple remain there; Bank request projection and wealth transfers belong to `ClassicBankingOperations`. Both use `ClassicMoneyTransferSupport` for package-backed movement validation and recalculation, so changing denomination movement or load behavior has one explicit owner. `test_money_workflow.gd` is the focused Bank and pooled-wealth characterization suite.

Battle opcodes enter through `ClassicBattleLifecycleOperations`, which owns start, resume, retreat, battle/death macros, age acknowledgements, and terminal handoff. The neighboring `CombatInteractionRequestBuilder` performs the separate read-only task of turning current combat state and rule legality into the typed `combat_action` request used by both scenario-owned and direct-session battles. Change combat mutation in the lifecycle or game combat owners; change detached command facts in the builder. Characterization begins in `test_scenario_vm.gd`, `test_reward_workflow.gd`, `test_combat_flow.gd`, and `test_session_persistence.gd`.
