# Application host

`src/app` is organized by the five jobs a maintainer encounters at the host boundary. `composition` contains the visible dependency root and shell alignment, `startup` contains first-frame and package preparation, `navigation` translates host input, `session` coordinates the replaceable playthrough plus saves and Character Files, and `platform` owns lifecycle, preferences, and debug-build facilities. None contains Realmz rules.

Follow an input from `ApplicationInputRouter` to a typed session command, and a committed step back through the presentation coordinator. Keep dependency construction explicit and keep campaign loading cancellable. Startup-sensitive changes require three warmed `startup_probe.gd` samples and the ordinary front-door test path.

`RealmzApplication._ready()` reads as five named phases: dependency construction, debug/movement binding, combat/interaction binding, shell/settings binding, and final startup. Add a dependency or signal to the phase that owns it; do not rebuild one long initialization procedure or hide the graph in an untyped service locator.

For lifecycle behavior, begin with `src/app/platform/application_lifecycle_host.gd` and the pure option/decision policy beside it. For adventure persistence, begin with `src/app/session/application_adventure_storage_host.gd`, then descend to `SaveHostController` and the storage repository. For reusable characters, begin with `src/app/session/application_character_files_host.gd`; its repository-facing controllers and detached revision views are neighbors in that feature. For responsive stage placement, begin with `src/app/composition/application_spatial_layout.gd`; map and battlefield geometry remain in their algorithmic presenters. The owning characterization is `tests/presentation/test_classic_ui_system.gd`, with repository and round-trip coverage in the save and session-persistence suites.

The lightweight entry composition is `src/ui/setup/startup_front_door.tscn`; after its launch card draws, it instantiates the directly editable `src/ui/setup/front_door_menu.tscn`. Keeping the menu scene outside the launch scene prevents its imported media from delaying the first frame. The same menu scene is mounted under the loaded shell when needed. `CampaignLibraryController` binds readiness, video and soundtrack lifecycle, and host signals without constructing controls. `src/ui/setup/campaign_selection_panel.tscn` owns its selected scenario, empty library, package progress, install, and refresh states; only its exported campaign row scene repeats for detached installed packages.

Party setup begins at `CampaignPartySetupController`, which composes the authored workspace with separate campaign-library, assembly, inspection, and character-creation controllers. Use the composition boundary for combined setup construction, visibility, layout, and Back behavior; use its named `campaign_library` or `character_creation` collaborator for those feature-specific operations. Buttons inside the workspace connect directly to the collaborator that owns the action, and no parallel forwarding API obscures that ownership.
