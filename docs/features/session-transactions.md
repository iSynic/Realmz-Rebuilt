# Session transactions

`GameSession` is the public adventure boundary: start, restore, submit an intent, respond to an interaction, inspect a detached view, snapshot, and close. It owns rollback, revision changes, request identity, and exact-once commit. Workflows receive an operation-scoped context containing the active content, state, RNG, VM, continuations, and revision services.

`SessionIntentCoordinator` is the command directory immediately behind that boundary. It groups exploration, magic/combat, party, and inventory/service intents, then calls the owning workflow without copying session state. `SessionCoordinatorResult` distinguishes a pre-transaction rejection, which keeps the current revision, from a committed failure, which advances the revision with its ordered events. `SessionContext` owns new-session initialization, accepted restore assignment, scenario reset, teardown, and detached snapshot construction.

`PlayerIntent` is the stable command-kind registry and typed envelope, not a catalog of every command constructor. `ExplorationIntents`, `InventoryIntents`, `MagicIntents`, `CombatIntents`, `PartyIntents`, and `EconomyIntents` are the discoverable feature entry points under `src/game/session/intents`. Their payload families name the values consumed by the corresponding workflow, while `PlayerIntentRegistry` only rejects a payload paired with the wrong stable kind. Add a command to its feature entry point rather than adding another forwarding method to `PlayerIntent`.

`InteractionRequest` is the small registry and wire envelope for pending player decisions. Feature-owned payloads live under `src/game/session/requests`: each file names the decision it carries, validates its own detached data, and preserves the established serialized kind and fields. Nested records use the common, service, combat, reward, or selection decoder that owns their shape rather than one public catch-all codec. Add a new request by defining its payload beside that family, registering its kind and codec centrally, then handling it in the owning workflow and UI binder. Do not grow another nested protocol catalog inside `InteractionRequest`.

`SessionContinuation` is likewise only the stable saved envelope for an interrupted transaction. Exploration, application, inventory, magic, service, and combat code create continuations through the matching factory under `src/playthrough/continuations`; each payload names the fact required to resume. `SessionContinuationCodec` alone admits their dictionary representation and rejects unknown fields, invalid resume combinations, or a payload paired with the wrong stable kind.

No UI, repository, Node, or wall-clock dependency enters this layer. New gameplay routes should add or reuse a typed intent and an owning feature workflow instead of exposing coordinator helpers. `test_game_session.gd` protects the command API, `test_scenario_vm.gd` protects the continuation wire denominator, and `test_session_persistence.gd` protects the complete saveable aggregate.
