# Purpose

- Own typed, focusable UI components for serializable `InteractionRequest` kinds.

# Ownership

- Components translate an existing request payload into controls and emit the exact response payload selected by the player.
- `InteractionComponent` exposes common hint and character-option scene paths as inherited editor defaults and loads them only at the construction boundary, avoiding a cold-import script/scene cycle.
- `classic_flash_overlay.tscn`, `locked_modal_shield.tscn`, `interaction_side_workspace.tscn`, `encounter_command_dock_host.tscn`, `interaction_application_workspace.tscn`, and `interaction_hint.tscn` own the presenter's conditional chrome. They remain editable components even though the presenter instantiates and positions them only for the active typed request.
- `TextChoiceInteraction` renders yes/no and authored indexed/scenario options as one backed content-width semantic response row. `InteractionPresenter` mounts that row in a compact floating pane immediately above the narrative well; it never consumes the narrative text measure or claims unused stage width. The shared presenter invents no generic title for these requests. A positive acknowledgement with visible authored text has no formal button or helper labels: clicking the narrative surface or pressing Enter/Space emits its one typed response. An authored empty positive message keeps that typed boundary and receives one content-width `Continue` action. Journal-eligible acknowledgements never add a separate Take Note button: source-backed default-off Auto Note leaves Castle's proven `N` key available, while an explicit enabled preference makes the narrative acknowledgement emit `{ "takeNote": true }`. An already-recorded message exposes no duplicate mutation.
- `InteractionPresenter` always presents a Complex Encounter's explicit authored prompt; prior AP narration or a prior result cannot replace the active Encounter request text.
- `encounter_interaction.tscn` owns the stable original-art Action, Items, Skills, Speak, Spells, and Stop dock directly above the narrative well and exports the editable Action, Items, Spells, Speak, and action-row scenes. `EncounterInteraction` classifies and binds request values without constructing stable layout. A new or repeated Complex Encounter starts with no command selected so its authored prompt retains the complete well. Action replaces the roster with Castle's actorless toggle-set sidebar: the request-owned choices scroll independently above fixed square Done and local Stop controls, Done enables only at the exact supplied count, and local Stop returns to the idle dock without backing out of the Encounter. Submitting an action removes the dock and sidebar while an authored click-result owns the narrative well; acknowledging a continuing result reconstructs the idle dock. Presentation must not invent a party-member choice for an authored Action such as COB's `Knock on the door`; Castle commits only the selected slot set. Authored Simple choices remain canvas-limited in one compact vertical list, while Speak alone uses the narrative well beneath the dock. A repeated Encounter keeps the latest non-click authored result in the well and uses a transparent pointer-blocking shield so the surrounding application remains legible without accepting background input. Items temporarily cover the application with the real `InventoryScreenController`; Spells temporarily replace the roster with a scroll-bounded `SpellsScreenController` in Encounter-selection mode; closing either restores the intact Encounter. Both submit the exact request-owned owner and identity. Skills uses a content-sized map-stage dialog whose previous/portrait/next controls form one centered cluster above the source-valued grid. Speak uses the established Theldrow input/action treatment, bounds its word-or-phrase entry to 39 characters so Castle's 40-byte destination remains terminable, and exposes Castle's one proven submit path. Escape first cancels an open action/item/spell task and otherwise emits only an authored Back/Stop response; it cannot invent an unavailable exit. Unavailable commands remain disabled in place with an exact reason, and every submission retains the typed complex-encounter body. Castle's Scroll-versus-Spells/Stop control mapping remains unresolved evidence and must not be guessed through presentation remapping.
- The shared `InteractionPresenter` under `src/ui/shared/interactions` owns request identity, modal visibility, and construction of `InteractionResponse`; this folder owns the typed request scenes it mounts.
- An interaction component may supply one semantic `preferred_initial_focus`; the presenter uses it before tree-order fallback. Treasure uses the already-selected recipient so opening the workspace does not falsely hover or focus-ring the first loot item.
- Treasure's Castle-shaped Money button uses the application-workspace overlay and retains that presentation state across typed denomination transfers. Closing it returns to the unchanged Treasure request; inline personal-transfer controls do not belong in the primary Treasure layout.
- `selection_interaction.tscn` owns the complete character-target context and surviving-allies layouts, including their alternate modes, headings, empty state, decision pane, and fixed Continue action. `SelectionInteraction` binds the active character prompt and optional spell context while `ClassicPartyRoster` remains the sole character picker, matching Castle's accessible right rail. The exact requested count auto-submits in stable Party order; no duplicate portrait grid or Continue control may consume the narrative well. Ally body-count selection instantiates only the exported `ally_selection_candidate.tscn` record scene inside its dedicated list.
- `LifecycleInteraction` renders only the host-supplied Main Menu/End Adventure or process-Quit operations in a compact locked floating modal. Process Quit shows one question and one centered content-width Save and Quit / Quit / Cancel row without duplicate headings or explanatory prose; every lifecycle request disables its outer interaction scrollbar, and Main Menu retains at most one short consequence line while showing every declared operation. It owns stable fixed actions, restrained destructive emphasis, and Escape routing to a declared Cancel action, then emits one declared action identity. It does not save, close a session, infer combat state, or reuse scenario-choice semantics.
- `ThiefEncounterInteraction` owns the dedicated eight-action workspace supplied by the typed request. It uses the same compact previous/next character navigation as Encounter Items, keeps the selected portrait/name above one full-height action grid, and emits the exact selected character and source action index. `PickLockInteraction` renders exact character identity, chance and countdown above its deterministic tumbler frames at the supplied cadence; the red, gold, and green track zones mirror Castle's thresholds, the final source second is held, and only the selected frame index is emitted. Neither component rolls RNG, recomputes ability values, mutates encounter flags, or invents a cancel outcome absent from Castle's picker.
- `thief_encounter_interaction.tscn` owns the visible character navigator, action pane, grid, and Back control. Its script instantiates only the request-sized `thief_action_button.tscn` collection.
- `pick_lock_interaction.tscn` owns the Pick Lock identity, mechanism, legend, action, and timer layout. Its script binds only the request values and instantiates `pick_lock_tumbler_row.tscn` once per supplied tumbler.
- Pick Lock starts its presentation timer only after entering a scene tree. Detached editor and test binding may render an exact supplied frame without starting wall-clock behavior; normal mounted interaction timing is unchanged.
- `interaction_response_button.tscn` supplies the common keyboard-focusable response control. `text_choice_interaction.tscn` and `lifecycle_interaction.tscn` own their stable panes, action hosts, and fixed controls; their scripts choose modes, bind detached values, and populate only request-sized choices. Feature-owned interaction scenes may reuse the same response boundary without returning to this generic folder.
- Encounter item mode uses the full application inventory workspace, including its standard portrait selector, ledger, character rail, item inspector, and explicit Back to encounter action. Its request-owned catalog binds the exact owner/instance pair to the hidden Classic identity without exposing hidden facts. The retained interaction accepts live layout-profile changes and rebinds this workspace at the new profile so a compact resize cannot preserve wide minimums or clip Back. Encounter spell mode filters the standard spellbook to request-supplied owner and packed spell identities; the controller changes only temporary caster, level, and spell selection before returning the exact typed pair. Disabled reasons come only from the request.
- A battlefield Ctrl/Command-click may replace the command overview with `BattleInteraction`'s read-only Items, Conditions, and Attacks record for the selected party or monster combatant. The persistent Back action restores the unchanged battle overview; inspection changes neither the active actor nor session state and renders only request-supplied rows.
- `SelectionInteraction` keeps mandatory field-spell, scroll, and charged-item target selection in the Classic textbox/Party-roster composition. It renders only the request's strict spell-target context—spell identity, selected power, effective cost, icon key, and target facts—while the roster owns numbered target picks and emits the existing stable-ID response. It uses the same native-slate target badge as field and combat spellbooks only for catalog-proven donor gradient lettering; unproven target types retain ordinary semantic facts without invented badge art. It does not parse prompts, recalculate costs, or invent target art for unproven Classic target types.
- `SelectionInteraction` also owns a locked floating surviving-allies modal with supplied candidates, health, required selections, maximum capacity, exact CICNs joined by stable ID from the detached completed-combat monsters or retained `party_allies`, and fixed Continue. It owns temporary selection and maximum enforcement and emits only selected stable IDs. An empty request has a non-trapping fallback, but core/session flow remains responsible for skipping ally selection when no allies exist.

# Local Contracts

- Never add gameplay facts, targets, prices, eligibility, or service availability that are absent from the request.
- Disabled controls require a specific player-facing reason.
- Every pointer action must also be keyboard focusable.

# Work Guidance

- Keep request-kind logic in the narrowest component and preserve payload field names exactly.
- Repeated combat spells retain explicit addition order, permit one through `maximumTargets`, and emit that order as `targetIds`. Summons retain clicked order, permit one anchor through `maximumTargets`, and emit that order as `targetCoordinates`. Memorized spells use the request's living combatant roster or battlefield pointer for selection and defer final legality to submit; scrolls retain core-probed candidates. Presentation cannot reorder the selection or commit gameplay state.
- Battlefield target cancellation emits no response. Confirmation preserves the existing combat payload ABI: one stable `targetId`, ordered `targetIds`, one legal `targetCoordinate` plus rotation, or ordered `targetCoordinates`, according to the configured mode.

# Verification

- Run `tools/verify.ps1`; interaction fixtures verify request-ID and payload preservation.
