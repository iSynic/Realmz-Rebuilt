# Workspaces and interactions

A major workspace has one scene whose stable hierarchy is recognizable in the editor, one controller that binds detached values and translates signals, and reusable row or card scenes for variable collections. A typed interaction follows the same rule but remains modal and emits only its declared response payload.

`InteractionPresenter` is the request binder, not a catch-all window manager. `InteractionComponentFactory` routes typed requests through explicit full-stage, narrative, party, workspace, and combat families and configures the selected scene without constructing its hierarchy. The presenter preserves request identity and translates the component's response. Its named `CombatInteractionController` binds only `BattleInteraction`: targeting, combatant focus, roster spellbook coordination, direct combat responses, and the exported Fast Spell dock. `InteractionOverlayHost` mounts the scene-authored shield, nested confirmation, Encounter dock, and side/application workspace frames; `InteractionFlashController` owns the retained queue for source-authored flash messages. Their geometry comes from `InteractionLayoutPolicy`, so changing a stable overlay begins in its `.tscn` scene while changing request classification begins in the policy.

Do not build panels, splits, tabs, headings, action rails, details, or empty-state regions with `Control.new()`. Export the row scene a collection needs, pool or rebind retained children, and keep layout values in the Inspector. The system manifest lists every major surface and the Realmz Builder preview registry must cover each one.

Complex Encounters begin at `src/ui/shared/interactions/encounter_interaction.tscn`. That scene owns the persistent six-command dock and exports the neighboring Action, Items, Spells, and Speak workspace scenes used by `encounter_interaction.gd`. The controller classifies authored actions, binds those stable scenes, and instantiates only the request-sized action-button collection; Inventory and Spells continue through their ordinary screen controllers so an encounter does not invent parallel item or magic UI.

Treasure begins at `src/ui/services/treasure_distribution_interaction.tscn`. The main scene exposes the ordinary loot field, recipient panel, item record, wealth actions, and Done control. It exports separate recovery, completion-confirmation, wealth-swap, loot-cell, vacant-slot, recipient, fact, and lore-caster scenes so all stable variants remain visible in Godot while the controller binds only request-owned items, recipients, facts, and legal actions. `tests/presentation/test_classic_ui_system.gd` characterizes the ordinary, compact, unavailable, unidentified, recovery, and completion paths.

Maps / Notes begins at `src/ui/journal/journal_screen.tscn`, and the folder README is its visual-maintainer map. The scene embeds the complete `maps_notes_workspace.tscn`, whose saved-place browser, current-note editor, historical-map viewport, acquired-map browser, cartographic stage and zoom controls, scrolling-text host, journal search, two-page book, empty states, and Wide/Compact reflow are editor-authored. Its exported location, player-map, and journal row scenes are the only variable UI records. `MapsJournalScreenController` binds detached values and presentation-local selection without constructing Controls; `ClassicMapPresenter` and `PlayerMapPresenter` remain the named algorithmic renderers.

Preferences and Game begins at `src/ui/shell/system_screen.tscn`, which embeds the complete `system_workspace.tscn`. Save/Load columns, fixed host actions, every setting row, all seven tabs, control-reference cards, diagnostics, empty/detail states, and Wide/Compact reflow are editor-authored. Only the detached save list instantiates `save_slot_row.tscn`. `SystemScreenController` binds host-owned `PresentationSettings` and save previews and emits existing host actions; it constructs no Controls and owns no settings persistence.

Party Wealth begins at `src/ui/services/services_screen.tscn`, which embeds the complete `services_workspace.tscn`. The pooled and banked totals, Pool and Share actions, adventurer ledger, selected-character exchange, three-denomination transfer region, persistent Done action, location-service panel, empty states, and Wide/Compact reflow are editor-authored. Detached characters, transfers, location services, and service actions instantiate the workspace's exported row scenes. `ServicesScreenController` binds only `MoneyWorkspaceView` values and rules-owned availability and emits typed money or service intents; it constructs no Controls and owns no economy rules.

Party creation begins in `src/ui/setup/party_setup_workspace.tscn`, which exports the five editor-authored wizard steps. `PartySetupCharacterCreationController` owns navigation, draft validation, and typed submissions. `PartySetupRaceCasteBinding` owns only the Race/Caste scene: it binds package-provided definition records, restrictions, compatibility, and detail labels through the shared setup state. `PartySetupAppearanceEditor` separately owns the appearance step, so changing either stable layout begins in its scene rather than in the wizard coordinator.
