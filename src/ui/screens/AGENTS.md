# Purpose

- Own scene-backed screens, reusable panels, and roster surfaces used by the canonical Classic-wide shell.

# Ownership

- Each route owns a registered scene. Scenes own durable header/layout, scrolling, focus containment, and the persistent Back action for ordinary reversible routes; `ScreenNavigator` supplies detached view content and routes that action through the same history path as Escape. Exploration, Combat, and Vault omit the generic action because their spatial or nested return surfaces own navigation explicitly. Inventory also omits the generic route action because its controller-owned Done action is integrated into the lower item record and emits that same Back path.
- `ClassicPartyRoster` owns the persistent six-slot right rail and Castle's single current-character marker. `party_roster_member_row.tscn`, `party_roster_empty_row.tscn`, and the scene-authored pointer-count label contain every stable control; the roster script constructs no Controls. No ordinary row latches independently: clicking another member moves the marker and changes character-scoped commands, while clicking the already-current member opens that exact Character record. Hourly exploration updates refresh matching existing rows in place from the new detached party records, preserving controls and selection while updating stamina, spell points, conditions, and portrait state. Its portrait stage follows Castle's `updatepictbox`: stamina below one receives exact CICN 2019 shading, and stamina below negative nine additionally receives exact CICN 2015 as the death marker through scenario-before-application media resolution. In combat, persistent Auto uses one compact `A` toggle with pressed-state and tooltip/accessibility explanation so all six rows retain an unobscured `HP current/max` summary and the stable party ID is the only mutation identity. A typed `CHARACTER_SELECTION` request switches that rail into Castle's separate countdown picker: a readable project-font cursor shows the initial picks remaining before any click, portraits receive descending numbers, repeated clicks renumber locally, and the exact count emits one Party-ordered response without opening the Character workspace. The request is mandatory under `FD-SCENARIO-002`: the picker exposes no cancel control and Back or Escape leaves the blocking request pending. Detached character-effect requests temporarily animate their exact CICN frame sequence over the matching portrait and then restore its current base presentation.
- The persistent roster owns one complete inset panel boundary around its title, slots, and scrollbar; it never appears as unframed text floating beside the spatial stage.
- During memorized combat spell selection, the roster reveals its embedded `combat_roster_spellbook.tscn` and hides the ordinary rows. The component scene owns the seven-level rail, spell browser, identity and rule facts, target badge, unavailable and description states, power strip, and fixed Cast/Back footer. `CombatRosterSpellbook` instantiates only exported spell and power-button scenes, returns the exact request-owned `CastOption`, and constructs no Controls; closing or resolving it restores the current detached party view and ordinary roster depth. One bounded records column contains the dense internally scrolling spell list, compact selected record, and power choices above the fixed action footer, so no detail can extend below the roster. Every detached known combat spell remains present: request-owned legal options supply cast powers, while known spells without an option remain selectable for inspection with an explicit unavailable state and a disabled Cast action. Its target badge preserves only catalog-proven gradient target lettering. The proven original Cast Spell and Abort controls remain visible at both supported compositions.
