# UI controller contract

## Purpose

Own route-local UI state and detached-view binding for scene-authored workspaces and variable record scenes.

## Local Contracts

- `classic_definition_toggle_list.tscn` owns the retained scrolling option host used by Character Creation. Its controller binds definition buttons into that authored collection and never creates the list hierarchy.
- Controllers receive an explicit target container and detached values; they never receive `GameSession`, repositories, or the owning router.
- `CombatInteractionController` binds one active `BattleInteraction` and owns its targeting, focus, roster-spellbook, direct-response, and exported Fast Spell dock boundary. The general `InteractionPresenter`, application input, and presentation coordinator address this collaborator directly; it never owns combat rules, battlefield rendering, or saved state.
- `BattlefieldInteractionController` binds detached `CombatView` input state to the algorithmic battlefield presenter. It owns tactical hover, inspection focus, Reveal Friends, movement-cost aid state, targeting rotation and confirmation, and typed movement/target response emission; it never draws the battlefield, mutates combat truth, or owns the rendered camera.
- Controllers emit typed intents, host actions, or presentation-setting changes. They never mutate gameplay state.
- Controller scripts reached by the background application graph must not script-preload imported textures or themes; resolve those resources only while constructing controller-owned controls on the main thread.
- `ScreenNavigator` alone mounts primary workspaces and owns route history. `WorkspaceFocusController` restores route focus and scroll state. The production scene owns the workspace and overlay hosts; neither the navigator nor a test harness may manufacture fallback hosts. Callers address `CampaignPartySetupController` and `ScreenContentPresenter` directly for their owned state rather than adding forwarding methods to the navigator.
- `ScreenContentPresenter` owns route-local controller composition, detached route state, content rendering, and route-specific audio. Its initialization groups signal relays by the system, character, inventory, services, maps, or spells controller that owns the source event. Its generic detached summaries instantiate the exported message and summary-card scenes; the router supplies the mounted route body and navigation-owned back label and does not render domain content.
- A controller may preserve selection, filtering, sorting, tabs, and draft text for its own route only.
- Application-route controllers own compact task-specific character selection inside their routed workspace. They do not depend on roster-row interaction, and item-local operations such as Trade keep their exact source item and recipient choices together.
- `SystemScreenController` exposes the host-owned traveled-area preview and Auto Note toggles in Controls plus the default-on Classic exploration-distance policy in Display. All persist only through `PresentationSettings`; map preferences change rendering from detached visited facts and Auto Note selects the acknowledgement payload, without mutating simulation directly. Its Audio tab keeps master, effects, and music volumes separate, persists global music enablement and source-classified Reduced Sound, and opens the shell-owned playlist modal without owning playback. Controls also owns the fixed keyboard/mouse reference derived from the public input contract; it does not imply unsupported remapping.
- `SystemScreenController` constructs no Controls and binds the complete scene-authored `SystemWorkspace`, instantiating only its exported detached save-slot row. Save & Load remains separate from Display, Audio, Pacing, Accessibility, Controls, and Diagnostics. Every preference tab uses a backed, vertically scrollable slate card so 800×600 at maximum text scale remains reachable; scene-authored rows align wide and stack in the compact `UiLayoutProfile`. Display pick lists use the shared Rebuilt-font option role in either typography mode. The Game menu exposes the full Save & Load route, and that workspace owns slot/source selection, one detached preview, and fixed host actions: Quick Save 1 retains legacy slot `quick`, Quick Save 2 uses `quick-2`, Save Selected overwrites the selected slot through the existing host boundary, and Save New Slot accepts only the repository's portable slot alphabet. A host-requested Save and Quit mode replaces ordinary save controls with one selected-slot Save and Quit action, while Back cancels that host mode. It distinguishes primary and backup loads and leaves corrupt/incompatible records visible with their exact reason. Preference tabs emit only existing typed presentation-setting changes and apply immediately; they never alter Classic rules or invent Apply/Reset, deletion, screenshots, schema mutation, or migration controls absent from the host contracts.
- `CampaignLibraryController` binds `front_door_menu.tscn` and `campaign_selection_panel.tscn`; it constructs no Controls. `bind_campaign_panel` accepts an existing scene instance for editor preview and tests, while the runtime construction path instantiates that same scene before calling the same binder. Those scenes own the Black Chancery identity, licensed looping application animation, separately looping click-enabled soundtrack, readiness-gated new/saved-adventure and Character Files actions, empty and selected-scenario states, and fixed package-operation host. Variable ready campaigns instantiate only the selector's exported `campaign_package_row.tscn`. The startup gate disables its three graph-dependent actions with one explanation and restores their original tooltips/focus atomically; Quit stays available. The controller separates one-time intro preparation, active playback, temporary suspension, and final resource release: the startup host may start the retained OGV behind its opaque card, ordinary route coverage never reopens it, and only final teardown releases it. The embedded video audio is never enabled, and the scene-authored independent MP3 player remains demand-loaded. It may resolve only the selected summary's exact `splashAssetId`; it cannot decode package content during discovery, classify free-form readiness errors, or retain terminal host failures absent from its detached operation view. External installation starts from one host file picker filtered to `.realmz2`; no developer path field appears in the ordinary library. Package progress disables competing install/refresh/scenario actions without displacing party controls. `CampaignPartySetupController` composes explicit shared setup state with independent inspection, party-assembly, and five-step creation controllers; `bind_setup_workspace` accepts an existing authored workspace and is shared by runtime construction, Realmz Builder, and tests. Its Load Saved Adventure action emits only a presentation route request to the package-bound System workspace. Those collaborators never inherit behavior from one another or receive the router. The composition controller owns setup construction, combined visibility, focus, and host coordination, while exposing the campaign library and character creator as named read-only collaborators. Callers address those owners directly instead of preserving forwarding methods; scene signals likewise connect directly to the assembly, inspection, or creation owner. Both public controllers mount under an explicit overlay host supplied by the shell scene.
- `PartySetupAssemblyController` owns one retained six-slot party-control set and updates its detached character, portrait, and availability values in place. Character-file rows may cache a prepared translucent drag texture keyed by revision and portrait identity; Add and drop continue to submit the same stable IDs, and neither gesture reads image pixels or uploads a texture on its activation frame.
- `PartySetupAssemblyController` constructs no Controls. It binds `party_assembly_browser.tscn`, instantiates only its exported Character File row, and rebinds the authored empty and pager states. `PartySetupInspectionController` likewise binds `party_setup_inspection_overlay.tscn` and instantiates only the shared character sheet inside its authored host.
- Party setup collaborators communicate through named public operations for assembly refresh, setup-option binding, import, inspection, creation lifecycle, and layout. `CampaignPartySetupState` exposes its shared host, campaign library, appearance cache, focus, availability, option selection, and child-clearing services explicitly; no controller reaches into another object's private methods or fields.
- `PartySetupCharacterCreationController` owns the full-stage five-step draft lifecycle, navigation, validation, and typed intent submission without constructing Controls. `PartySetupRaceCasteBinding` owns the authored Race/Caste step, source-backed definition filtering, compatible-first Caste ordering, detail records, and selection callbacks. Race drives the left/right selector relationship; each Race and Caste record pairs a narrow pressed selector with a wider detached detail, named-compatibility pane, and source-backed rule facts. Empty source descriptions occupy no UI and never become invented fallback prose. The binding may suppress only literal numbered fallback labels and cannot infer compiler provenance or calculate modifiers. `PartySetupAppearanceEditor` binds the Appearance scene's paging, catalog frames, alternate states, exact-media previews, and hidden selectors; each variable grouping instantiates only `appearance_thumbnail_row.tscn`. Appearance exposes exact package portrait/tactical catalogs as paged two-row, six-column grids labelled from explicit `recommended_race_ids`; it never infers grouping from labels or numeric ranges. Portrait selection may follow the proven Classic resource pairing until the player independently overrides the tactical icon. Review consumes the detached provisional `CharacterView` through the shared complete character sheet; it may resolve that view's exact appearance and item media, but cannot calculate rules, invent restrictions, or substitute resource identities. Starting Spells shares `ClassicSpellSelectionChrome` with the ordinary spellbook, keeps only presentation-local level/focus state, and emits the complete typed selected-ID set so choices on hidden levels survive filtering. Pressed state communicates selection without modifier-key helper copy. `CharacterSpellOptionView` supplies the exact Classic resolution-effect resource sequence; the creator may animate only those IDs through scenario-first application-media resolution and must not derive art from a numeric spell ID. Actions remain outside the scrolling record body.

## Verification

- Route lifecycle tests own primary-workspace exclusivity and modal input ownership; do not add one test per overlap symptom.
