# Scenario runtime

Compiled scenario definitions are immutable game content. `RealmzContent.scenario` is the program graph, while `RealmzContent.scenario_records` exposes `ScenarioContentCatalog` for messages, option labels, triggers, and direct encounter definitions. The execution boundary has four visible systems: `classic/` adapts Castle opcodes, `actions/` owns Safe Scenario Action evaluation and mutable action state, `runtime/` provides the session-owned operation API and continuations, and `vm/` schedules typed execution records. Scenario Actions are reusable callable programs; call sites do not contain executable gap behavior.

The matching playthrough boundary lives under `src/playthrough/scenario`. `SessionScenarioCoordinator` joins the public session transaction to application hooks, suspended VM handoffs, party-defeat revival, and exact return to the owning world or combat operation. `ScenarioApplicationHookWorkflow` resolves the authored hook program and execution context, while `ScenarioContinuations` and `ScenarioApplicationContinuationBody` preserve only the hook and suspended-handoff facts needed across save/restore.

Under `src/scenarios/classic`, begin with `ClassicOpcodeCatalog`, follow the registered handler, and enter the named operation. `ScenarioClassicExecutionRules` applies source-backed code replacement, the separate manual GOSUB stack, native positions and encounter repetition to `ScenarioExecutionState`. `ScenarioVm` schedules the ordered Classic, Safe and operation records, pending response and trace. One runner-local counter bounds the entire external entry, including retained child work and returns.

Classic invocation records retain entry mode, phase, position, guards and the explicit encounter exit. Shared Classic state retains active code, independent destination header/selected AP, retained GOSUB flag and manual return values. Reaching record end does not pull GOSUB. Safe records retain `ScenarioExpressionScope` and typed iterators; a Classic timeline gains a lexical scope only when an explicit ordered Safe call needs one. Program overrides resolve once on admission to each new code record. Domain mutation remains in the existing operation and rules owners.

VM schema 5 and save v9 define the replacement boundary, including exact decimal-text tagged Safe integers and the native header inside VM state. ADR 0029 and `scenario-execution-contract.md` define the complete acceptance gates. Combat, timers and application hooks use explicit child records under that runner. The strict legacy codecs flatten admitted v5-v8 callers before assignment; v9 rejects the old nested execution forms. Loading never writes, replays or invents unavailable history. Preserve a v8-or-earlier save to return to Beta 27, which cannot read v9. Bounded verification and remaining certification limits are recorded in `scenario-vm-evidence.md`.

Mutable scenario truth does not live in the VM or in an undifferentiated `GameState` dictionary. `ScenarioProgressState` owns searched cells, quest values, journal discovery, and source-ordered selected characters. Its `ScenarioEncounterState` owns timed encounter overrides, eliminated choices and results, attempt counts, thief flags, and program redirects. Both remain pure game state and write the existing flat save fields, so this readable in-memory boundary does not change save representation.

Keep dictionaries at package and save codecs. `ScenarioRuntimeContinuation` is only the stable versioned envelope for a suspended operation. Interaction, age, service, combat, and reward code construct the corresponding typed body through the feature factories in `src/scenarios/runtime/continuations`; `ScenarioRuntimeContinuationCodec` alone accepts their dictionary representation. Begin with `tests/scenario/test_scenario_vm.gd`, which protects all 38 stable wire kinds; reward and battle-return behavior is owned by `test_reward_workflow.gd`. Castle evidence explains behavior but does not become a second host architecture.

Execution records and program transfers carry `ScenarioExecutionContext`, the live typed provenance for triggers, encounters, application hooks, battles, and program transfers. Ordinary execution-state copies stay typed. Only `ScenarioExecutionContextCodec` translates that value to or from its sparse save dictionary, so adding provenance has one obvious wire owner and cannot quietly reopen dictionary-driven execution.

Service opcodes enter through `src/scenarios/classic/operations/classic_service_operations.gd`. Shop and Temple remain there; Bank request projection and wealth transfers belong to `ClassicBankingOperations`. Both use `ClassicMoneyTransferSupport` for package-backed movement validation and recalculation, so changing denomination movement or load behavior has one explicit owner. `test_money_workflow.gd` is the focused Bank and pooled-wealth characterization suite.

Battle opcodes enter through `ClassicBattleLifecycleOperations`, which owns start, resume, retreat, battle/death macros, age acknowledgements, and terminal handoff. The neighboring `CombatInteractionRequestBuilder` performs the separate read-only task of turning current combat state and rule legality into the typed `combat_action` request used by both scenario-owned and direct-session battles. Change combat mutation in the lifecycle or game combat owners; change detached command facts in the builder. Characterization begins in `test_scenario_vm.gd`, `test_reward_workflow.gd`, `test_combat_flow.gd`, and `test_session_persistence.gd`.
