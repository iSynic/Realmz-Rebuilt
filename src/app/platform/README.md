# Application platform

The opt-in Runtime Testing Bridge is split between strict framing/retry policy (`runtime_testing_protocol.gd`, `runtime_testing_connection.gd`, `runtime_testing_endpoint.gd`), detached observations/checkpoints (`runtime_testing_observer.gd`), and explicit host binding (`runtime_testing_host.gd`). It is disabled by default, debug-build-only, and read-only for live adventures. See [runtime testing](../../../docs/runtime-testing.md) for the wire and launch contract; this does not alter Providence's preview protocol.

Fixture launch validation and preparation live in `runtime_testing_fixture_request.gd` and `runtime_testing_fixture_session.gd`. `runtime_testing_commands.gd` translates bounded names into public host/session commands; `runtime_testing_ui.gd` delivers actual viewport input to visible controls. Named setup is not ordinary campaign-start proof, and direct invocation never certifies an authored caller or travel route. Revisions remain monotonic across restore; screenshots wait for the matching post-draw boundary.

Use this folder for behavior owned by the Godot process rather than the Realmz simulation. `application_lifecycle_host.gd` handles Quit, End Adventure, and Save and Quit; `application_lifecycle.gd` holds the testable decision policy. `application_settings_controller.gd` binds presentation preferences, `debug_tools_host.gd` keeps the default-off AP/random-rectangle preference available through F12 while restricting typed mutations and event tools to debug builds, and `development_preview_request.gd` validates the strict request Providence uses to launch an isolated development preview.

Lifecycle cancellation must leave the process and playthrough untouched. Presentation settings never enter deterministic state or adventure saves. Retail UI may expose only the presentation-owned F12 Diagnostics toggle; developer mutations, logging, console state, and fixture facilities remain absent. Preview requests must use absolute temporary paths, exact package hashes, the named deterministic party, and supported typed targets. Map targets retain canonical map identity and map-local coordinates; scrolling targets retain the signed ID of an exact scenario-owned `TEXT` resource; Complex, Thief, Extra Action Point program, Battle, Treasure, and Shop targets retain native record identities. A Thief target also carries its exact owning Complex Encounter and enters through that owner's ordinary Thief action. Extra Action Point program preview validates exact XAP ownership and runs in a standalone context that does not claim Timed, hook, item, random-rectangle, or other caller semantics. Direct Shop preview is deliberately unrestricted because opcode-73 acceptance ranges belong to the caller rather than `Data SD`. Execution cannot install packages or touch player storage. Begin with `tests/presentation/test_classic_ui_system.gd`, the settings repository tests, and native startup smoke checks.
