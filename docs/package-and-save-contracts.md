# Package and save contracts

## `.realmz2`

A deterministic ZIP contains canonical minified JSON and content-addressed media:

- `manifest.json`: format/version, campaign/content IDs, compiler provenance, engine requirements, start location, capability inventory, file hashes, package hash.
- `content.json`: Realmz definitions and text.
- `world.json`: maps, authoritative topology, APs/XAPs, transitions, random rectangles, timed encounters, and immutable metadata.
- `scenario.json`: Classic instructions, Scenario Action programs, state definitions, and migrations.
- `assets/index.json` plus hashed media payloads.

Providence owns the schema. The runtime mirror under `contracts` is byte-identical and independently enforced. The package excludes editor layout, absolute paths, native raw bytes, compatibility annexes, and archaeology artifacts.

Schema v2 replaces the unpublished v1 contract. The mirrored schema is SHA-256 `42e8a3de0dff78efaed680581e696a76bca2e5c09124230e2f0d41a2c28844c9` from Providence commit `76dccf38`. It retains the v1 world, scenario, media, and direct Realmz definition contracts while adding typed campaign display metadata (`name`, `version`, `author`, `contact`, `description`, and `splashAssetId`), party/level restrictions, race/caste descriptions and eligibility relationships, each race's exact five-by-fifteen signed aging table, distinct bounded monster `requiredWeapon` and `magicToHit` fields, and complete Classic battle-terrain catalogs. Battle `distance` remains a separate initial-placement input. Providence's canonical project and native compatibility annex remain outside the package.

The schema-v2 world contract uses normalized directional edges and explicit features; Castle's packed dungeon fields and Providence's Layout record remain compiler inputs, not runtime map models. Each cell names a base tileset/tile and a nullable image-overlay asset. Placed AP references compile in native record order and retain `classicRecordIndex`; duplicate record identities on one map fail runtime validation. Placed AP headers compile to a typed `postActionLocation`; XAPs use `null`, and tile mutation remains an explicit scenario instruction. Random rectangles retain signed 1-in-10,000 chances, battle ranges, three random-door slots, only/option behavior, and media IDs. Its content contract carries direct Simple/Complex/Thief/Timed Encounter records, a distinct Classic option-label table, and direct race, caste, item, spell, monster, battle, treasure, and shop definitions. Providence merges 799 nonzero bundled Classic item identities with scenario supplies/overrides and compiles standard Data S records to packed class/level/slot identities; custom Data Spell slot 0 is packed ID 5101 and slot 104 is 5715. Monster weapon restrictions retain the signed Data MD byte as `requiredWeapon`; `magicToHit` is its independent weapon-plus threshold. Battle records retain their unrelated placement `distance`, explicit monster slots, coordinates, and traitor inversion. Its scenario contract contains trigger/program references, preserved `ClassicAction` instructions, typed `CallScenarioAction` instructions, compiled Safe bytecode, versioned action-state definitions, and migrations. It does not contain Safe visual/source AST, behavior anchors, authoring modes, or sandbox source.

For every package with a reachable battle, `world.json` now carries immutable `battleTerrainSets` and each map identifies its effective set. A land set contains its active landlook records 0 through 200 followed by shared `Combat Data BD` records 201 through 400; the active landlook therefore wins Castle's overlapping tile 200 exactly once. The dungeon set contains shared records 200 through 400. Every tile retains signed sound, time, solid, boat, and forest values, exact boolean flags, and the 3×3 `combatBuild`; incomplete ranges or malformed builds fail both export and runtime construction. These are immutable construction inputs, not an alternate exploration topology. Tactical positions, battlefield generation, proximity-gated melee, ranged attacks, and withdrawal attacks remain runtime-disabled until session-owned combat geometry is implemented and serialized.

Managed Providence media and decoded imported resource-catalog pictures/icons/sounds become content-addressed payloads. Classic resource identity is the exact four-character type plus signed ID; case and trailing spaces are significant, and equal numbers in `PICT`, `cicn`, and `snd ` are unrelated resources. Scenario-managed media replaces the imported scenario-catalog entry for the same key, imported scenario media wins over stock media, and shared stock media only fills unclaimed keys. Providence rejects any duplicate asset ID or exact resource key left after applying that chain, and the runtime rejects the same ambiguity independently. The compiler also resolves shared Classic `snd ` resources referenced by runtime-reachable AP, XAP, Simple Encounter, and Complex Encounter instructions when no scenario or managed asset already claims that identity. WAV payloads are normalized to include RIFF's required pad byte after an odd-sized terminal chunk before hashing and packaging. Every referenced map tileset is a required content-addressed PNG with explicit grid metadata; Providence normalizes Classic PICT 302's fixed dungeon-composition region to a 4×4 runtime atlas. Classic negative land values compile as the landlook's base terrain plus a content-addressed `cicn` overlay rather than masquerading as a tileset index. Absolute paths and resource-fork bytes never enter the package.

`PackageRepository` rejects unsafe/extra entries, noncanonical entry order, schema or capability drift, per-file size/hash mismatches, package-hash mismatches, malformed topology, duplicate identities, unresolved map/trigger/program/action references, unsupported Classic opcodes, invalid Scenario Action namespaces or callers, argument/type mismatches, oversized Safe programs/arrays, and unknown capabilities before constructing `RealmzContent`. `realmz.scenario.gdscript-actions-v1` is a recognized but unavailable capability and fails readiness until an OS-confined external host exists.

Installed-package discovery is deliberately staged. It verifies the manifest, schema/capabilities, deterministic archive inventory, and every declared file size/hash so corrupt or stale packages do not appear playable, but it does not parse the 65 MB AOGM world document or construct 72,900 cells merely to draw the campaign list. Generic discovery retains every immutable content-hash revision for diagnostics; the campaign selector groups valid revisions by campaign ID and exposes the most recently installed file only. Older revisions remain intact and can still be opened explicitly. Selecting Play runs the full document/reference/topology validation and typed construction above. An unchanged immutable package load is cached in memory by canonical path, modification time, and byte count; installation of the file already at its content-hash destination does not validate it a second time.

## `.r2save`

A versioned envelope under `user://saves/<campaign-id>/` records the campaign and package hash, rules/deviation IDs, complete game state, overlays, clock, economy, equipment escrow, allies, encounter attempts/type flags, mutable shop stock, combat active-turn facts, per-character melee/missile mode, and exact fumbled item instances, scenario-program replacements, VM frames, VM or session-owned pending interaction, post-move/random-region/AP-destination, direct combat-death-macro, post-battle ally-selection, or fumble-recovery continuation, Scenario Action state, RNG state/draw count, and metadata.

Each serialized character stores `ageDays` and the independent Classic `ageGroup`. The group cannot be reconstructed from age alone after a spell jumps multiple ranges because Castle applies only one neighboring row per operation. Save envelope v3 is unchanged: prerecord nested characters without `ageGroup` remain readable and infer their group from the package's authored race range, with the caste minimum as the fallback for legacy placeholder ages.

A pending `age_update` uses the existing interaction wire shape and a bounded session or VM continuation. Direct clock work may retain an unstarted post-move continuation beneath the age queue; scenario spells retain the issuing VM frame. Each response advances exactly one ordered dialog, and the envelope remains v3 because no top-level field or wire representation changed.

A pending `treasure_distribution` with mode `fumbled-item-recovery` names the completed battle, exact item instance, legal recipients and disabled reasons. Recovery handles one queued item per response after body-count selection and before the battle after-message. The battle queue and active-turn physical-action fact are additive nested v3 state; older v3 saves default to an empty queue and no prior physical action. Restore validates item-instance uniqueness across inventories, party storage, and the battle queue, and validates a direct recovery request against the deterministic payload before replacing the active session.

Battle weapon modes are also additive nested v3 state. New battles initialize Castle's melee-first toggle from validated type-2/type-15 equipment. Older v3 combat snapshots without `characterWeaponModes` remain readable and default to melee; they do not infer a new missile selection during restore.

Saves occur only at committed boundaries. Infrastructure writes a temporary file, reads and validates it, rotates one backup, and atomically replaces the slot. Restore validates an entire replacement before changing the active session. Schema migrations are ordered pure transforms with fixtures.

Party assembly is also a committed save boundary. Before Begin, the party may be empty or partially assembled and `partySetupCompleted` remains false; finalized and imported characters already belong to session state. A completed campaign state must contain at least one character. Add, remove, import, and Begin are typed session intents rather than presenter-local edits.

There is no Classic or prior-Remake save importer.

## `.r2char`

Reusable character revisions are separate from `.r2save`. A record contains a stable character ID, immutable revision hash, rules version, source campaign/package provenance, publication metadata, complete detached character state, inventory/spells, and source revision. `CharacterVaultRepository` stores revisions under `user://characters/<character-id>/`, validates readback, retains one recoverable backup, and archives instead of deleting. Import is a typed session intent; eligibility failures identify missing definitions, restrictions, level limits, or incompatible race/class relationships. Publishing never happens implicitly as a side effect of playing a campaign.

`SaveRepository` writes envelope v3 by creating a temporary file, parsing it back into typed state, rotating one backup, and renaming the verified temporary file into the slot. Ordered pure migrations take v1 through v2's session-interaction/random-region fields and then add v3's `actionPointDestinationDepth` to nonempty post-move continuations. V3 also validates the alternate direct combat-death-macro, post-battle ally-selection, and fumble-recovery continuation shapes against their matching combat and pending request. `GameSession.snapshot()` returns a detached aggregate, including all gameplay-domain state, VM frames, pending request/continuation, Scenario Action state, and host continuation. Restore constructs and validates replacement state, RNG, VM, action-state, session-interaction, and continuation objects before replacing the active session.
