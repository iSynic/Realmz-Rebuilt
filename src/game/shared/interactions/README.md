# Shared interactions

Start with `InteractionRequest` to understand the stable kind registry and wire envelope, then use `InteractionResponse` for the value returned by presentation. This folder owns those pure cross-boundary contracts, neutral request bodies, and strict decoder dispatch. Character, economy, combat, and scenario-specific bodies live beside their matching game models. Every body contains only detached transaction data, serializes through `to_data()`, and never reaches into live session state.

When adding or changing a request, update its feature-owned body, the matching dialog, selection, thief, service, or reward decoder here, its response type, and the owning gameplay and presentation tests together. `interaction_request.gd` registers the stable kind and dispatches only; it does not decode feature fields. Nested records decode through the common, service, combat, reward, or selection value decoder; `InteractionValueDecoderSupport` contains only shared wire-shape predicates. Keep serialized kind names, field names, versions, and optional-field behavior stable unless an explicit save migration owns the change.

Neutral bodies here cover acknowledgement, indexed or binary choices, character or ally selection, lifecycle, and general selection. Character-owned age and level decisions, economy-owned services and Treasure, combat commands, and scenario-owned encounters and Pick Lock remain top-level types under their `src/game` feature folders. The central request class remains the small registry and codec entry point; it must not regain feature payload implementations.
