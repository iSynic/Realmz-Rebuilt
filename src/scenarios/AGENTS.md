# Scenario execution contract

## Purpose

Own the serializable Scenario VM, Classic instructions, Safe Scenario Actions, capabilities, and the single Realmz runtime API presented by a session.

## Ownership

- `classic/` owns Castle opcode identity, registration, handlers, control-flow transitions, and source-backed domain operations.
- `actions/` owns Safe Scenario Action evaluation and mutable action state; immutable compiled definitions remain in `src/game/scenario`.
- `runtime/` owns the session-constructed API, execution context, result/handoff records, and strict suspended-operation continuations.
- `vm/` owns instruction/frame/trace/limit models and execution pacing.
- `SafeExpressionEvaluator` owns bounded expression, declared-value-type, and ordered call/instruction argument evaluation. `ScenarioVm` owns frames, action operation/call/set/condition/return phases, suspension, and transaction pacing.
- `ScenarioClassicControlFlow` owns Classic AP/XAP program transfer, encounter-result/repeat, GOSUB-depth, and encounter-exit frame mutations. It returns a typed `ScenarioDirectiveTransition`; `ScenarioVm` alone applies halt, timeline completion, frame return, and trace publication.
- Classic AP, XAP, encounter, GOSUB, return, and result semantics.
- Scenario Action execution, private helpers, state schemas, and migrations. Immutable compiled definitions live in `src/game/scenario` so game content never depends outward on the executor layer.
- Capability declarations and readiness checks.

## Local Contracts

- The VM is presentation-independent and serializable at every interaction yield.
- Scenario execution depends only on game models/contracts; immutable instruction and program records cross inward from `src/game/scenario` without importing executor behavior back into core.
- Domain mutations execute through one session-owned `RealmzRuntimeApi`; there are no Godot ports or dynamic GDScript fallbacks.
- `RealmzRuntimeApi` is the single VM boundary and delegates source-backed Classic work to typed domain executors under `classic/operations`; those executors cannot bypass `GameState`, `RealmzRules`, or the session RNG.
- Classic GOSUB depth is 20. Safe Action call depth is 32, program size 4,096 nodes, arrays 256 entries, and execution 65,536 steps.
- Unknown instructions, IDs, capabilities, actions, and response shapes fail explicitly.
- Safe Scenario Actions may request explicit elapsed minutes through the time capability, but they do not expose the player-facing Camp/Rest workflow as a capability. Camp mode, held Rest pulses, random interruption, and movement departure remain session-owned typed intents and continuations.
- Packages cannot override `realmz.*`; campaign actions use `scenario.<campaign>.*`.
- A Scenario Action call is an ordinary AP/Encounter timeline entry. Authoring gaps and behavior anchors are not runtime concepts.
- Runtime instruction forms are preserved `ClassicAction` records and typed `CallScenarioAction` records. Safe bytecode is compiler output, never Providence editor state.
- The session owns the active VM, action state, runtime API, and post-move continuation. VM snapshots include Classic and Safe frames, origin, trace, and any pending typed interaction.
- VM frames and program transfers carry a closed `ScenarioExecutionContext`; raw context dictionaries never enter live execution. `ScenarioExecutionContextCodec` alone preserves declared trigger, application, encounter, combat, and program-transfer provenance and rejects unknown saved fields.
- A Classic interaction-resumed program branch inherits the issuing frame's trigger and map provenance, while its target frame resolves its own program override and caller context. Encounter or Safe Action classification may not leak from the suspended source frame.
- A saved Classic program replacement is resolved once when a frame starts. Redirecting the active AP changes that frame explicitly; neither behavior rewrites immutable package programs.
- Classic XAP transfers inherit the issuing frame's AP origin/context. Loading macro code cannot erase the retained trigger identity used by opcode 25; a legitimately source-less XAP still ends cleanly because Castle's opcode has no player-visible missing-origin failure.
- Battle opcodes resolve the Classic battle ID from Extra Code slot zero when a row is present; the action operand is only the direct-ID form when no Extra Code row exists. Opcode-2 mode 10 retains Extra Code slot two in the typed battle caller as its authored post-loss XAP target, so a positive target runs as a nested GOSUB and the issuing frame continues at its next slot after revival; rows without a positive target retain the restart fallback.
- Battle-round and monster-death macros run as serializable nested VM frames. A death macro receives the defeated combatant ID and must complete before occupancy, allegiance, and battle outcome are finalized; `FD-COMBAT-007` retains the pending subject's footprint so CODE 119 revival remains positioned and saveable. Spell-triggered death macros drain from the combat state's save-owned queue before the issuing caster advances. The host may not clear allegiance merely because a queued macro completed; an authored operation such as opcode 119 owns that mutation.
- Typed combat-action requests expose all eight session-probed player directions and exact disabled reasons. In melee mode, an opposed occupied direction carries the stable hostile combatant identity and remains a typed move response; the game resolves Guard-before-contact and collision melee without moving. Missile Target/Fire remains a distinct actor-target response. The runtime API does not infer targets, positions, allegiance, or movement legality from presentation state.
- A manual typed combat-move response may carry the boolean `autoSwitchToMelee` application preference. The runtime defaults absent legacy responses to false, rejects malformed values, and delegates the exact projectile-profile, manual-actor, Guard-order, switch, sound, cost, and attack transaction to `CombatFlow`; it never applies the preference to direct or automatic actions. Preference-off hostile projectile contact plays Castle warning sound 6000 and returns to the unchanged combat request rather than failing the scenario continuation.
- Typed combat-action requests expose the battle-owned character weapon mode, exact legal mode switch, and source-owned ordinary projectile targets. Missile mode omits melee attacks; Fire carries the actor and selected stable target ID and remains disabled with an exact reason for unsupported projectile classes or failed range/LOS/resource gates.
- Typed combat-action requests expose source-admitted spell and power choices without eagerly expanding their actor or coordinate targets. Automatic groups carry no fabricated target ID; spatial types 3 and 4 carry the rules-owned Data AD shape, ordered offsets, every source-admitted orientation mask, and default battlefield coordinate, and the response returns only the chosen coordinate and rotation. The runtime API never rebuilds area masks, range, LOS, or affected actors from presentation state; it submits the selected target to the authoritative game probe once.
- Typed combat-action requests also expose source-probed charged spell-item options with exact item-instance, spell, power, actor, ordered repeated-actor candidates, ordered summon-anchor coordinates, automatic-group, ray, or rules-owned spatial target facts. Authored power eight first exposes a target-free roll action, then regenerates the same VM request with its activation-owned power and `powerStaged` marker; save restoration must preserve that exact request. Repeated responses preserve one through power distinct stable actor IDs in player selection order; summoning preserves one through power ordered battlefield coordinates; other responses return only the appropriate stable target ID or selected center/orientation. The runtime revalidates and commits charge/load, action resources, sound, effect, and continuation through `CombatFlow`. It never treats an item use as a memorized spell or accepts an arbitrary script fallback.
- Typed combat requests expose rules-owned Auto Turn, Delay, Bandage-recipient, and Turn Undead probes plus sorted persistent-Auto IDs. A `set_auto` response changes only the named living party character, and enabling the active actor may enter the same bounded automatic activation transaction immediately. The runtime preserves mandatory VM/death-macro yields and never automates across them.
- Classic opcode 1 preserves the message operand sign as control flow. A positive message yields a typed, saveable `acknowledge` request for the dedicated Classic textbox and may record its representable Data SD2 identity through an explicit `takeNote` response; a negative message publishes its presentation event and continues without a click or fabricated note action. The runtime accepts only message IDs 0 through 2,999 for journal discovery under `FD-MAPS-002`; Auto Note remains a separate preferences gap.
- A Classic or Safe time operation and Classic opcode 17/18 spell that changes an age band yields a typed `age_update`; its runtime continuation owns the ordered remaining updates and resumes the exact issuing VM frame only after every response.
- Classic opcode 3 treats zero option IDs as the standard Yes/No pair. Nonzero IDs resolve through the package's Data OD option-label table, with ordinary message lookup used only for old-format packages that have no option-label table.
- Complex Encounter spell responses preserve authored slot order. Each slot first compares the exact packed Classic spell ID, then a nonzero authored value below seven compares the resolved spell class; other casts take the authored fallback result without consuming RNG.
- Thief encounters and ability-reading opcodes query the character's trained-ability array. They never substitute the separate twelve-slot racial combat-modifier array; the unauthored fifteenth trained slot remains zero under `FD-CHARACTER-001`. A sprung trap applies damage first, then resolves its optional authored spell once across the selected character or stable whole-party target set through the game scenario-group spell contract.
- Classic opcode 30 filters candidates using each iterated character's own attribute or trained ability and applies a negative index once as select-on-failure under `FD-SCENARIO-001`; Castle's action-slot alias and attribute-only double inversion are not reproduced. Opcode 31 preserves the separately observed undefined-attribute path: it asks for one living character, consumes one Rand(25) draw, keeps that identity selected, and continues without either XAP. Its selection remains mandatory under `FD-SCENARIO-002`; Castle's A-abort fallthrough to party slot zero is not reproduced.
- Classic opcode 9 publishes the absolute `snd ` resource ID while preserving the operand sign as presentation playback metadata: positive is asynchronous and negative waits within the Classic sound queue. It never blocks or advances simulation.
- Classic dungeon opcode 37 requires all five Extra Code values. On dungeon entry, the signed fifth value has absolute heading 1–4; a negative sign locks the authored view policy to 3D and a positive sign permits multiview. It is not a sound ID. Opcodes 96 and 97 respectively lock and permit dungeon multiview in save-owned state; presentation alone chooses the current 2D/3D view and honors Wizard's Eye.
- Classic opcode 68 owns party fatigue through the world/time handler. Modes one and two set exhausted/rested to 135/4; mode three reads its authored percentage from Extra Code slot two, multiplies before integer division, truncates toward zero, and clamps through the same 4–135 state bounds under `FD-SCENARIO-005`. Imported signed values remain preserved package input rather than a runtime migration.
- Classic opcode 74 alters only selected characters with nonzero maximum spell points. For each target it consumes `abs(Extra Code 0)` source-ordered range draws but applies only the final draw with the count's sign, clamps current points to zero through maximum, and preserves Castle's lower-range-bound sound identity defect before the optional message.
- Classic opcode 52 snapshots its incoming picked set for Picked Only, evaluates only those candidates, and then replaces the set; its exact-position selector uses validated one-based positions 1 through 6. Opcode 53 separately preserves Castle's clear-before-check source-mode-two result. Opcode 55 uses selector zero for any picked character, selectors 1 through 6 for their one-based party positions, negative `-N` for at least N picked characters, and a safe authored failure for unsupported positive selectors; failure behavior one follows its authored XAP branch while behaviors zero and two finish the current code stream.
- Classic opcode 89 resolves its exact authored monster record and otherwise fails explicitly. The `scenario-tutorial` package alone corrects its invalid missing record 149 to source-backed Goblin Shaman record 116; a package that supplies record 149 keeps it, and no other campaign inherits the correction.
- Classic opcode 41 permanently eliminates one exact one-based option from any package Simple Encounter and continues its issuing code. Opcode 35 uses the same save-owned set for the current encounter, but immediately reopens its remaining choices without replaying the opening cue or consuming an ordinary repetition. The saved choice continuation replaces the abandoned result while preserving its caller and repetition counter.
- Classic opcode 81 branches only when every character in the whole-party, nonempty picked, or one one-based party-position set has the authored condition. Valid but unoccupied positions and empty picked sets take the failure branch; unsupported selectors fail explicitly. It ignores Castle's unused third message slot and carries GOSUB to either XAP.
- Classic opcode 58 compares Castle's signed saved difficulty directly against its compiled threshold. Its branch mode zero targets an XAP; modes one and two transfer within the active Simple or Complex Encounter to the selected result and zero-based code cursor. The typed VM directive preserves that cursor across GOSUB and save-owned continuations; keep and erase behaviors end the complete issuing timeline.
- Classic opcode 59 must preserve the `newland.c` defect: it reads the authoritative faced cell and removes up to three 1000-valued marker bands, but never compares the normalized tile with Extra Code slot zero. Behavior slot one therefore branches unconditionally through the same XAP or active-Encounter result/cursor directive as opcode 58; Keep Codes and erase end the issuing timeline.
- Classic opcode 71 stores whether X/Y facts are hidden. Opcodes 93 and 94 enable and disable the compass respectively; only a request for the already-active state publishes Castle's warning. All three flags are save-owned and publish presentation refresh facts without consuming time or RNG.
- Classic opcode 26 is Castle's separate `flashmessage("Click Mouse", 350, 100, 0, 30005)` boundary. It yields one saveable compact-click acknowledgement and publishes stock sound 30005 exactly once when executed; adjacent opcodes such as 71 retain only their own mutation and redraw behavior.
- Classic opcode 67 sums raw charges for the exact Classic item across the party and selects its success or failure destination. Opcode 72 branches only when every quest in its inclusive range is set, with Castle's vacuous true result for an inverted range. Opcode 75 tests picked or all eligible living non-Animated characters for sufficient spell points and preserves Keep Codes on its authored failure mode. Each admits XAP, Simple Encounter, and Complex Encounter destinations through one typed branch contract.
- Classic opcode 85 publishes its optional sound and text in source order, consumes exactly one inclusive destination draw, and then enters the selected XAP, Simple Encounter, or Complex Encounter. A serializable encounter-origin frame owns the selected identity, attempt count, signed GOSUB return, final-result exit, and opcode-34 unwind so retries and restored repetitions never rerun opcode 85 or consume another draw.
- Classic opcode 57 changes one arbitrary land level's save-owned landlook and darkness without loading it. Opcode 70 saves or restores one exact map, coordinate, and land/dungeon context; its restore suppresses the issuing AP header relocation. Opcode 78 tests the authoritative faced cell for shore, boat requirement, path, LOS, fly/float, forest, or exact normalized tile before branching to XAP, Simple, or Complex Encounter. Opcode 92 applies signed chance and inclusive rectangle changes to an arbitrary land or dungeon region from its ten compiled operands without mutating package maps; Castle's negative-map seek and out-of-range rectangle behavior safely normalize to map zero and fixed rectangle slot zero.
- Classic opcode 20 relocates the party and continues the issuing timeline when the destination cell has no placed Action Point. A destination AP marker alone requests the bounded destination recheck and replaces the issuing timeline, matching Castle's `field[x][y]` gate even when that destination record is disabled or fails its chance roll; opcode 45 remains teleport-only and never rechecks.
- Classic opcode 44 preserves Castle's process-global Complex Encounter record: a Complex result marks result 1–4 of that active record, while a Simple result marks the last Complex record loaded by the runtime when one exists and otherwise completes without a typed record mutation; later selection terminates through the slot-seven Keep Codes equivalent without changing package programs. Opcode 125 destroys the stable bounded set of living monsters matching the independent Classic name byte, honors Castle's loyal-monster inclusion and zero-to-100 limit semantics, and drains ordinary death macros through a typed continuation before terminal battle resolution.
- Classic opcode 84 is the obsolete scenario-registration gate, not a reserved instruction. Like opcode 98's application-registration gate, it completes through the explicit control-marker path because Rebuilt has no commercial registration state or restriction.
- Classic opcode 95 changes the save-owned dungeon heading directly for operands one through four. Every other operand consumes exactly one Castle `Rand(4)` draw and stores its one-through-four result; fixed headings consume no RNG.
- A Classic shop continuation exposes identified immutable stock plus native-slot save-owned buyback stock and only player-knowable carried-item identities. Buy, sell, paid identification, equipment/range rejection, wealth, stock, and sound 683 are revalidated and committed through the session-owned rules/state boundary before the same typed request is regenerated.
- Classic opcodes 32 and 49 configure contextual temple and bank availability; they do not force a presenter open. Entering a contextual Shop or Temple first runs its package application hook through the session-owned VM, then opens the nested typed service continuation. Direct scenario opcodes 6 and 32 do not run those contextual hooks. Temple owns bank transfer, nine fixed services, Pool/Share controls, and exit warning. Entering a bank imports all three banked denominations once and exposes the ordinary Pool/Share/exact-Swap operations through one typed continuation; Done does not re-bank, while location departure does. Bank-backed shop and temple exit return all pooled denominations. No-bank exit-to-manual-Swap and contextual money changing remain explicit unavailable boundaries.
- Classic opcode 24 ends the complete current timeline and preserves the issuing placed Action Point without rewriting its program. Opcode 39 transfers only active execution; Keep Codes must neither persist that temporary XAP nor overwrite an explicit opcode-7 replacement. Opcode 34 instead unwinds every result/XAP frame through the rewound issuing encounter, clears its typed encounter provenance, and resumes at the following authored slot. Without Keep Codes, the session disables the AP after successful completion. Opcode 25 is Castle's explicit in-program removal operation: it disables the issuing AP and immediately terminates the complete timeline, including after a staged treasure continuation, so a rewound Encounter cannot reopen.
- Completed battles may yield a typed `ally_selection` from the issuing combat continuation. That response rebuilds the held-over ally party under Castle body-count limits before the scenario frame continues.
- A completed battle prepends its exact fumbled-item queue to the ordinary `classic-reward` continuation after `ally_selection`, matching Castle's single booty workspace. Fumbled instances are identified but otherwise retain exact instance state; assignment or discard must finish before the battle after-message and issuing frame continue. The request and VM continuation are save-owned. A direct legacy fumble-request adapter remains presentation-testable, but incompatible save v4 files are not decoded and new sessions do not create that request.
- Ordinary scenario and battle rewards use one `classic-reward` continuation. Treasure assignment, leave-behind confirmation, Pool, Share, denomination Swap, Detect Magic, Identify Objects, every earned level result, and eligible spell selection all resume through the issuing VM/session frame. Under `FD-REWARD-001`, one committed reward repeatedly subtracts the current caste threshold and publishes one saveable acknowledgement per level until that recipient's carried victory points are nonpositive; the recipient then receives at most one spell-selection stage. This corrects Castle's single-check close, which defers already-earned levels and makes later small awards appear to trigger them. Detect Magic and Identify Objects independently recompute caster eligibility from remaining spell points after either action; their request records stay visible while treasure remains and expose an explicit completed/unavailable reason instead of disappearing. Do not restore the removed loot/level player intents or add a parallel mutation path.
- Reward and temple Pool, Share, and Swap reuse the core's ordinary denomination rules, recalculate every affected character's Classic movement, and publish their exact source sounds. Scenario continuations cannot retain a separate wealth/load model.
- A completed victory prevalidates every nonsummoned monster plus all potentially generated loot identities before claiming `rewards_started` or consuming reward RNG. Persisted summoned instances contribute no experience, wealth, authored loot, parchment, ration, validation, or reward draw. Each ordinary monster then consumes the source-ordered gold, gem, jewelry, parchment, and ration draws admitted by its exact flags. Opcode-2 mode 5 discards monster wealth and authored loot while preserving experience, fumbled items, and eligible incidental drops. Mode 10 instead bypasses ordinary terminal stages: victory restores captured equipment/wealth and returns once without reward RNG; total defeat retains that escrow and restarts its issuing program. Reward construction and every resumed operation are deterministic transactions: failure restores canonical game state and RNG, retains the retryable continuation and fumbled queue, and publishes no speculative events. Opcode 48 additionally prevalidates and persists its source-ordered fixed-treasure stage. Completion marks `rewards_completed`, appends the after-message, and returns once only after every stage closes.
- Classic opcode 122 delegates to the game fumble operation only after Castle's outer party-active and committed-physical-action guards. A failed outer guard suppresses authored Extra Code media. The unreachable nested monster branch is not implemented; natural monster fumbles belong to `attack2`, not this opcode. The live `inspell` guard remains explicit until spell activation owns a source-equivalent lifecycle fact.
- Scenario-launched battles that trigger Classic monster aging wrap the issuing Classic or Safe combat continuation in a serializable typed age-update queue. Acknowledgement resumes remaining monster turns, Guard/withdrawal cursor, battle/death macros, completion, or the next player actor without restarting the issuing scenario instruction. A Guard that kills a death-macro monster retains that cursor and footprint; CODE 119 revival continues with the next queued reaction rather than replaying or discarding the interrupted sequence.
- Scenario-launched Escape yields a `yes_no` request owned by the issuing Classic or Safe combat continuation. Decline returns to the unchanged active turn; acceptance commits the core's per-character Escape and then resumes battle, body count, the fumble-leading ordinary reward queue, and the issuing VM frame in their ordinary order. The nested confirmation must survive VM/save restoration without replaying the combat action.
- Scenario-launched total-party defeat ordinarily suspends the advanced Classic or Safe operation frame into a typed host handoff. The session saves that frame and its post-move or post-clock owner while Global Party Death runs; unrecovered defeat closes without executing later instructions, while opcode 119 revival suppresses rewards, releases combat once, and resumes the exact caller. Opcode-2 mode 10 deliberately bypasses that handoff, revives each character to one stamina, clears Animated, preserves equipment escrow, and, when Extra Code slot two names a positive XAP, runs that XAP as a nested GOSUB before the issuing program continues at its next authored slot; a row without that target retains the strict restart fallback, all without consuming RNG. Opcode-56 target-minus-one backup/experience-loss return remains explicitly unavailable.
- Scenario-launched combat responses preserve repeated-spell `targetIds` as an ordered array of stable actor IDs and summon `targetCoordinates` as an ordered array of battlefield anchors. The runtime rejects mixed actor/coordinate target sequences, validates the complete response shape, and passes it to the same game probe used by direct-session casting; it never sorts, deduplicates, places, or resolves targets in the host.
- `ClassicOpcodeCatalog` owns the complete parity denominator for opcode numbers 0 through 127 plus signed forms -14 and -23. Each identity is executable, source-reserved, or an explicitly owned pending implementation; only executable identities enter package readiness or handler registration. A declared executable opcode must have an explicit handler and may never fall through to dynamic dispatch or a silent no-op.
- Opcode 29 targets one of Castle's twenty `Data MD2` player-map records, not a playable land level. Positive operands acquire once and publish Castle's exact acquisition text plus stock flash cue 30005 for ordered application presentation; negative operands acquire once and yield a typed saveable acknowledgement carrying the player-map presentation identity. Resume returns through the issuing VM frame exactly once. Missing records and malformed responses fail explicitly without recording a false identity.
- A debug encounter may run one validated Classic encounter instruction through an ephemeral `ScenarioVM` program. That program exists only for the active developer interaction, never resolves package overrides, and is deliberately excluded from snapshots; normal package programs and save restoration cannot name it.
- Debug victory may complete only a base Classic or Safe combat request. The VM retains the issuing typed continuation until the runtime has accepted the completed battle, then enters the same ally, reward, after-message, directive, and caller-frame path as ordinary terminal combat; nested retreat, age, macro, or death-macro waits cannot be bypassed.
