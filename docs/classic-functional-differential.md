# Classic functional differential

Classic-visible behavior is developed through a rolling differential gate. Current Remake identifies existing functionality, mappings, tests, and likely differences. Castle source controls the behavioral decision; a controlled Castle runtime fixture is used only when complete source flow is insufficient. Providence must preserve the authored inputs, and Realmz Remake 2.0 must own the result through typed runtime boundaries.

Content ownership follows Castle's application/scenario split. Realmz Rebuilt ships the stock Realmz rules records, strings, fonts, controls, and integrated media once; Providence emits only original scenario-owned content, normalized stock references, and source-proven exact-key overrides. The runtime composes those authorities before constructing a session. The first text family migrated to this boundary is the 252 player-spell descriptions in the pinned `The Family Jewels` negative `STR#` records. The integrated media families begin with all 142 `snd ` resources from that same application fork. The composed media catalog checks the scenario package first only for an exact type-and-ID override, then the application catalog; an ambiguous package key fails instead of falling through. PICT and CICN migration remains family-specific while those workflows still require package asset IDs. Schema v3 still duplicates several stock definition tables; that is recorded package-contract debt and not permission to expand campaign ownership.

The machine-readable record is `tests/fixtures/oracle/classic-functional-differential.json`. It contains the detailed paths, symbols, commits, expected traces, tests, decision state, and links to the application workflows those cases support. This document summarizes only the current conclusions.

Differential cases provide depth for behavior already investigated; they are not the completeness denominator or the default scheduler. The fixed denominator and parity-convergence batch live in `tests/fixtures/oracle/classic-application-workflow-inventory.json`. Its deterministic [status report](classic-application-workflow-status.md) separates complete-application gaps from route coverage, individual opcode ownership, and modern host work. A functional workflow receives more differential archaeology only when ordinary play exposes a discrepancy, a reachable blocker or high-risk boundary depends on it, Providence may lose authored data, or source ambiguity affects a target campaign. Every differential case and workflow link is validated bidirectionally.

The current combat-command tranche separates Auto Turn from saved character Auto and derives all command availability in core rules. Persistent Auto commits one character activation at a time and yields to the host before continuing. Turning a roster toggle off during playback settles that presentation transaction and commits the queued change before continuation; Escape disables every party Auto toggle at the same boundary. Combat AI is an explicit improvement boundary. Player Auto assigns relative likelihood weights to legal immediate-action categories for bleeding, critical healing, Turn Undead, ally-safe supported spells, melee, missile, and movement; ordinary monsters do the same for physical contact, authored missile/cast preference, critical healing, and supported spells. One serialized session-RNG draw chooses between competing categories, while exact spell/power, target, safe placement, and route selection remain deterministic; forced and single-option actions do not spend a choice draw. Hard immunity, reflection, and allied area footprints suppress unsafe damage choices. Neither side performs multi-turn search, guesses unsupported cure specials, learns probabilistic resistance outcomes, or models absent persistent hazards. Pursuit tries the legal direct step and then deterministic battlefield routing toward a reachable valid opponent, treating later actor occupancy as temporary while retaining walls and footprints; Castle's bounded shifted probes are the no-route fallback. Delay and manual Bandage expose two source defects rather than silently copying them: `FD-COMBAT-012` prevents a last-slot Delay from immediately selecting the same actor, and `FD-COMBAT-013` restricts Bandage to one actual living bleeding recipient. Round progression preserves the party-ordered bleeding ticks and Castle's default second warning-sound draw after individual survivor sounds. Turn Undead preserves source-order targets, the signed `canSummon` exclusion, threshold and experience formulas, eight-frame effect identity, death-macro boundary, and once-per-battle state. These five workflows are functional from synthetic evidence; ordinary AOGM acceptance remains the current certification target. The follow-on Undo slice records only actor, activation-start cell, round, cursor, and availability. Result-free movement may be undone after save restoration; attacks, reactions, spell/item results, or turn advancement close the boundary. `FD-COMBAT-014` rejects Castle's unchecked occupied-cell overwrite. Repeated Undo and initiative-edge re-entry remain unresolved until controlled Castle runtime fixtures exist.
