# Application composition contract

## Purpose

Own the Godot composition root and translate host input/output into the pure session boundary.

## Ownership

- `composition` owns the visible composition root, explicit dependency graph, spatial alignment, and short host-status wording.
- `startup` owns the first-frame boundary, campaign package preparation, cancellable package work, and detached package-operation views.
- `navigation` owns named host input routing and the complete application input-action vocabulary.
- `session` owns the replaceable `GameSession`, adventure persistence coordination, Character Files and vault workflows, and combat-response translation.
- `platform` owns process and adventure lifecycle, presentation settings, and debug-build tooling.
- `RuntimeTestingHost` connects the explicitly opted-in developer loopback endpoint to injected application owners. Live endpoints reject mutation before dispatch and export only detached observations or the public validated snapshot contract. Network framing never executes gameplay outside the main-thread boundary; release startup cannot enable testing.
- Application and host collaborators address `GameShellStatusController`, `GameShellCommandController`, the persistent roster, and the navigator's setup/content controllers as their actual public owners; `GameShell` does not forward those APIs.

- `StartupFrontDoor` owns immediate process entry and background construction of `RealmzApplication`; `RealmzApplication` constructs the gameplay dependency graph explicitly.
- `GameSessionController` owns the replaceable `GameSession` instance and publishes committed steps.
- `ApplicationInputRouter` owns keyboard, pointer, and normalized controller routing policy; `RealmzApplication` constructs it and remains the gameplay input entry point. `StartupFrontDoor` constructs the same controller owner only when its deferred menu becomes interactive, then releases it before application handoff so startup and application never listen concurrently.
- `ApplicationInputRouter` may invoke only the composition root's public input, availability, and lifecycle-query operations; it must not reach into private host fields or methods.
- `GameSessionController` materializes one detached `GameView` per committed revision and shares it with host input checks and presenters; host code must not rebuild the same revision repeatedly. It also retains the presentation-requested map-cell span across session replacement and may rebuild that read model at the same gameplay revision when responsive layout changes.
- Detached campaign and package-operation views live with `startup`; detached Character Files identities and revisions live with `session`. `CharacterVaultRevisionView` is app-owned while remaining `class_name`-compatible. Prepared package views expose the core `MediaSource` abstraction and never leak a storage package catalog into presentation.
- This boundary coordinates repositories and presenters but contains no Realmz rules.
- After the application character library validates, `ApplicationCharacterFilesHost` asks the vault controller to install the trusted six-record starter catalog only when the vault is absent or completely empty; catalog or staging failure is a nonfatal startup diagnostic and ordinary character creation remains available.

## Local Contracts

- No gameplay autoloads, service locators, `GameGlobal`, `NodeAccess`, or string-based dispatch.
- The composition root and its host controllers use registered class names directly. Do not hide dependency identity behind `*Type` or `*Script` preload aliases; explicit construction remains readable at the call site.
- The startup front door keeps engine boot black and gives its first runtime frame only the Rebuilt card, opaque black backing, and entry/exit audio streams. Its `_ready` starts exact application sound 624 with the already-visible card and returns before loading the theme, fonts, menu controller, slate, or gameplay graph. After the first rendered frame, it loads the menu dependencies, prepares and starts one retained silent OGV decoder behind the opaque card, background-loads and retains the application root script, then chains the complete application scene through a second `ResourceLoader.load_threaded_request`; imported presenter textures and shaders are instance-loaded on the main thread instead of script-preloaded so the worker parser never owns those resources. Three seconds after entry it starts the exit 624 while retaining the card, then hides both card layers, reveals the already-playing menu, and starts sound 20 in the callback that follows the complete 1.513-second cue. Scenario, saved-adventure, and Character Files actions remain disabled until construction finishes; Quit remains available, only an actual load failure exposes Retry, and no custom worker thread parses scenes. The hidden application receives no input and suppresses its duplicate intro decoder until the front door transfers ownership through public shell routes.
- The controller may call only the public `GameSession` operations.
- Interaction UI responses enter through `GameSession.respond`; presenters never resume the VM or mutate state themselves.
- After a successful interaction response, the composition root may compare detached before/after journal counts and request one transient journal indicator only when the committed view gained an entry. A successful host save similarly requests one transient save indicator. These presentation signals do not enter session state, and the host must not imply an autosave when no autosave operation exists.
- `ApplicationAdventureStorageHost` owns application-level save, backup restore, and save-preview operations. It receives the active immutable content explicitly for each operation, delegates storage to `SaveHostController`, restores through the public session controller, and clears only transient queued combat Auto changes after a successful restore. It never owns save records or gameplay state.
- A committed `character_publication_requested` event is the only creator-to-vault write boundary. `ApplicationCharacterFilesHost` snapshots the already-finalized session character and asks `CharacterVaultController` to publish an immutable revision; rejected/declined interactions and ordinary campaign mutations perform no vault write.
- `ApplicationCharacterFilesHost` owns the no-scenario Character Files workshop. After the first frame it starts the pinned Providence-built stock catalog on the package host's dedicated worker, keeps standalone creation and campaign start visibly unavailable while that load is pending, and applies the detached result on the main thread. It attaches the validated application definition/media baseline before any scenario prewarm or start, so exact-ID scenario overlays compose before portable character items resolve. It then runs the same typed creator transaction through `CharacterCreationSession` and publishes the completed detached character directly to the vault. Selecting a scenario continues to use that scenario's `GameSession`, so package-specific Race/Caste definitions and restrictions never leak into the application-wide stock creator.
- Vault listing converts each validated immutable revision into a detached `CharacterVaultRevisionView` against the selected campaign content so setup can inspect eligible and ineligible records without importing or mutating them. Its public fields and `from_record` factory behavior remain unchanged; presentation consumes the view without defining, duplicating, or compatibility-wrapping it.
- Restore constructs and validates a replacement before swapping the active session.
- Main Menu is the player-facing host route over the End Adventure lifecycle and public `GameSession.close` boundary. The host prompt never enters `.r2save`; after confirmation, the session runs End Adventure and then Party Death package hooks, exposes any typed hook interactions, and closes only after both return without revival. Save-and-return starts that chain only after transactional save success, active combat never offers a save, and noncombat gameplay interactions remain modal. A completed close returns to the unloaded application splash; campaign-library browsing alone does not close gameplay.
- Process Quit is a separate host-owned typed confirmation. Menu and window-manager requests share one path after disabling Godot's automatic quit acceptance; an active noncombat session may choose Save and Quit, which releases the modal and opens the existing save-slot workspace before any write or termination, while battle cannot save. Cancel explicitly releases host interaction ownership so Quit can be requested again; cancellation or save failure leaves the process and session untouched. A pending host lifecycle confirmation owns response routing before standalone Character Files creation or session interactions. Quit never runs the scenario Global quit hook. `configure_lifecycle_host` may replace the save host and terminal process callback only before scene readiness so the real composition can be proved without terminating the test runner; ordinary construction retains production defaults.
- Campaign discovery is a responsive manifest-only library operation over the Castle-distributed bundle and user installations. A valid user-installed revision wins over its bundled campaign baseline. Choosing Play starts one cancellable storage worker for full integrity validation and immutable installation, including on first use of a bundled campaign; the composition root polls detached progress, joins the worker at its terminal state, and mutates neither media nor session until the validated result is available. Session-start failure leaves the previous media catalog untouched.
- After the retained front-door video and hidden application shell are stable, the composition root may ask the package host to prewarm the last successfully started campaign resolved through that same discovery list. Successful session start alone persists its stable campaign identity; failures never change it, no package path persists, and matching claim or different-campaign supersession retains the ordinary validation and cancellation boundary.
- Storage progress and repository records are converted to app-owned detached view models before presentation. Presentation code may not consume storage DTOs directly.
- Named `InputMap` actions are the host input boundary. `ApplicationInputRouter` preserves the priority between debug tools, playback controls, combat inspection, Back, typed interactions, route shortcuts, and exploration commands. Land movement binds the complete keypad compass, including 7/9/1/3 diagonals; the host suppresses those diagonals on dungeon maps before creating a typed intent. Camp, Rest, and Heal are separate typed commands; held Rest, Heal, and Area Search cadence is presentation-owned and emits one intent per pulse. The router catches physical mouse release so rerendering the pressed footer button cannot strand a held command. During a manual character activation, physical Alt press/release owns the transient Fast Spell dock and Alt plus top-row `1` through `0` invokes the matching binding through the ordinary combat response; focus loss always releases that presentation state. While battlefield targeting is active, `T` cycles and marks a supplied combatant or marks the current/default area center; Space confirms that visible target through the same typed response as its pointer controls. Back first asks the active typed interaction to cancel its local subtask or emit a declared cancel/back response, then resolves passive media, contextual drawers, and route history; when none owns the input in free Exploration, it opens the System workspace. Pending interactions suppress route and exploration input.
- Controller dispatch gives exactly one owner priority in this order: binding capture or text editor, locked modal, radial, combat playback or targeting, focused workspace, then exploration. The on-screen editor mutates only its local draft until Done returns text to the original field; it never submits that field's surrounding action. Controller binding Apply reconfigures only the normalized owner after validation and persistence.
- When the optional first-person dungeon presenter is active, the host translates Up/W/8 and Down/S/2 into forward/reverse absolute movement from the detached save-owned heading, translates Left/A/4 and Right/D/6 into typed quarter-turn intents, and rejects diagonals. First-person forward/reverse movement preserves that heading. The top-down dungeon renderer retains absolute cardinal input and submits the distinct typed overhead-move semantic that aligns the same save-owned heading before collision, so its arrow and a later 3D view cannot disagree. During exploration, Space asks presentation to toggle dungeon 3D/2D; a locked authored policy remains 3D unless the detached party has Wizard's Eye.
- The composition root owns one `HeldMovementController` shared by keyboard and mouse exploration. It submits one immediate typed single-step movement, requires a 150-millisecond hold before repetition begins, then uses the persisted 25–400 percent cadence from twenty scheduled steps per second at 100 percent without entering `.r2save` or simulation state. That same exploration percentage scales the first-person dungeon's camera-only move and turn transitions; Reduced Motion snaps those transitions while leaving intent cadence unchanged. A changed held direction requests its first step immediately, and ordinary blocked attempts retain the physical hold so the player can steer away without releasing. A completed placed AP that leaves the party on the requested adjacent cell and creates no interaction also preserves the hold, matching Castle's loop after `newland`; a modal, combat, transition, encounter boundary, or AP relocation stops it. The scheduler emits at most one step per rendered frame and never catches up missed intervals. The same host settings boundary applies 25–200 percent combat playback speed, the optional traveled-area preview, source-backed default-off Auto Note behavior, Classic/readable typography choice, separate effects/music volumes, global music enablement, twenty playlist modes, and source-classified Reduced Sound policy to presentation only.
- While combat playback is active, the composition root rejects gameplay, route, and interaction input before it can reach the session. Space skips only the presentation transaction. Roster persistent-Auto toggles and the Escape full-Auto abort are the only gameplay exceptions: the host queues each stable character ID and desired boolean; turning one off settles current playback immediately, commits the queued change, and applies it before deciding whether to run the next one-activation Auto transaction. `PersistentAutoCoordinator` retains one pending continuation until playback, queued toggles, transient interaction overlays, lifecycle dialogs, and controller suspension clear; it waits for the committed battlefield to cross a rendered-frame boundary, then rechecks session identity, revision, active actor, and Auto state before submitting one existing typed response. A failed revision pauses with a visible reason instead of retrying. Escape queues Auto-off for every enabled party character and resumes manual control at the next activation boundary. Battlefield target clicks and Back/cancel remain host translations into the presentation-owned target state; only a completed target payload crosses the existing `GameSession.respond` boundary.
- A terminal session step reached during combat playback does not navigate to setup or campaign selection until `PresentationCoordinator` settles the retained battlefield and publishes that exact committed step. Host teardown and navigation therefore happen once, after presentation releases the prior view.
- `ApplicationSpatialLayout` translates the shell's centered bounded application rectangle to the map, battlefield, dungeon, and interaction presenters, requests a detached map projection matching every complete visible cell in that rectangle plus the presenter's one-cell retained guard on every edge, and reapplies interaction geometry after resized shell containers settle so an active AP pane cannot mask the reflowed footer. Responsive projection size and its guard are read-model configuration only; those settings and coordinates never enter the session or save aggregate.
- The application injects Auto Switch to Melee only into a manual typed combat-move response. The core owns eligibility, source ordering, mutation, and any pending one-move continuation; no application preference object crosses into `GameState`.
- Direct-session battles expose a detached combat request while remaining intent-driven. The composition root translates that request's typed response body into the corresponding combat intent; scenario-owned combat continues through `GameSession.respond`. Both paths preserve the same presentation component, core legality contract, and ordered spell, scroll, or charged-item summon anchors.
- Every build binds physical F12 to one `DebugToolsHost` from the front door through active play. The host accepts the named action or raw keycode and edge-latches a physical-key poll as an exported-build fallback without double toggling. While the front door owns input, it temporarily hosts that same dialog and restores it to the application before handoff. Retail exposes only the presentation-owned Diagnostics surface and its default-off persisted AP/random-rectangle map overlay. Debug builds additionally expose direct-text warp, unsaved no-clip, party restoration, encounter and battle injection, forced victory, recent Auto history, and the default-off backtick/tilde console shortcut; each mutation becomes a typed public `SessionDebugCommand`. Held no-clip submits a quiet adjacent command without repainting debug status per tile, so it shares the ordinary incremental presentation cadence while bypassing collision and AP execution. The selectable bounded console translates committed combat and clock events into readable records with a raw fallback. Retail, saves, and ordinary gameplay intents never carry developer mutations, logs, console state, or flags.
- The export-excluded Providence preview scene attaches a strict `DevelopmentPreviewRequest` before `RealmzApplication` enters the tree. The application then uses default presentation settings with result-sibling scratch save/settings paths, skips campaign discovery, Character Files, recent-campaign persistence, and package installation, and delegates package validation plus target entry to `DevelopmentPreviewSession`. The ordinary session controller and presentation coordinator still own every visible state change. Public release startup contains no preview scene or host script.

## Work Guidance

- Keep dependency construction visible in `RealmzApplication`.
- Convert Godot input into typed intents and interaction responses before entering `src/game`.
- Battlefield Ctrl/Command-click inspection is a presentation-only host route: forward the hit-tested stable combatant identity to the active battle component without submitting an interaction response or mutating the session.
- Keep process Quit, campaign-library navigation, and the Main Menu/End Adventure lifecycle as distinct host operations. Do not turn session close into a free-standing gameplay intent.
